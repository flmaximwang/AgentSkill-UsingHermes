# Authoring and extending skills in this pack

How a skill in this repo is written and edited, once the mechanics live elsewhere: installing/updating is
`install-hermes-skills` / `update-hermes-skills`, the scan gate is
`install-hermes-skills/references/install-hermes-skills-scan-gate.md`, renames are
`install-hermes-skills/references/install-hermes-skills-renaming-a-skill-pack.md`, and the structure
trees are generated by `scripts/auto-generate-skill-structure.py` (`scripts/README.md`). This file is the
convention layer over those.

## Prose

- **English prose, source-language evidence verbatim.** Write the body in English; keep the original
  Chinese tables and real command output exactly as they are. The verbatim output is the receipt —
  translating it destroys the thing being cited. New sections inherit the file's already settled prose
  language; drafting in the source language is an easy drift, so re-read the whole delivered file before
  reporting and convert any paragraph that switched.
- **Flag the evidence tier inline.** Mark inferences as inferences ("mechanism inferred, not measured")
  and keep measured facts separate from derived ones. State where a claim comes from
  (`tools/skills_hub_github.py:171-174`) or show the real output.
- **Router over encyclopedia, but no truncation of verified facts.** Push depth into references; never
  drop a verified fact to keep the body short. Body under ~200 lines; a reference past ~300 lines gets a
  short contents list at the top. Long is fine in a reference, never in the body.
- **Order multiple routes as a ladder, never as a menu.** When one file must cover several ways to do the
  same job, rank them best-to-worst (best = least maintenance **and** most complete result), state the
  ranking criterion outright, and give each rung three things: when to use it, what you get, and its
  **drop signal** — the observation that licenses stepping down. Tell the reader to walk the ladder
  top-down and drop only on a signal, warn against choosing a lower rung because it looks simpler, and
  never offer a lower rung as an "alternative" while a higher one works. A flat list of methods reads as
  a defect, so converting an existing flat list into an ordered ladder is a valid request in itself.
- **Do not restate the connected system's own docs.** Copying a tool's parameter list or a repo's file
  map into a skill duplicates always-loaded context and goes stale silently. Cite where the fact lives
  instead, and spend the skill's words on the workflow and the pitfalls.
- **A measurement enters a delivered package only re-run or cited.** Every measured claim is re-run before
  it goes in — never against the live profile, since a probe that mutates the real home makes the removal
  or update it performs real and wrong — and never restated from memory. Where it cannot be re-run, write
  it with the session and message id that produced it. A number carried over from a local skill loses its
  receipt in the move, and prior-session measurements are the facts that quietly rot.

## Structure and house style

- Directories are named **操作-对象**: `<verb>-<object>`, with the verbs fixed by `README.md`
  (install / remove / maintain / update). Your reading of what a skill "really does" is not a verb.
- Every reference is prefixed with its own skill name (`<skill>-<topic>.md`); the frontmatter carries
  `name` + `description` only.
- **Content that already has a home in the pack is merged into that umbrella's references**, not added as
  a sibling skill: material about the skills subsystem belongs in the `install-` / `update-` / `remove-` /
  `maintain-hermes-skills` references. A merge means the route table and the `description:` of the
  receiving skill have to name the new entry point in the same edit — depth behind a route row nobody
  reads never loads.
- A rename is never local; it cascades into reference filenames, cross-skill pointers, the generated
  trees and every profile's install record
  (`install-hermes-skills/references/install-hermes-skills-renaming-a-skill-pack.md`).

## Triggering

A skill loads when the consuming agent reads the list and calls `skill_view`; nothing matches a
description mechanically. So a description true of **every** turn cannot select a turn, and it never
fires: on a live profile more than half the skills on disk had never been loaded, and the split ran along
whether the description named something recognisable in the current turn. Write the description so it
names a tool, a system, a file type or the artifact the skill produces, and keep the condition
evaluable — *"load at the FIRST message of a session …"* is false afterwards, which is what lets the entry
discriminate. Measured numbers, the per-feature load counts, and the two config keys that make a load
certain (`skills.auto_load`, `channel_skill_bindings`) are in
`maintain-hermes-memory/references/inspect-hermes-skill-usage.md`.

## Frontmatter — the two failures that look like prose problems

- **An unquoted `: ` inside `description:` breaks the YAML frontmatter.** YAML reads it as a nested
  mapping and the whole frontmatter fails to load; Hermes then falls back to a naive line parse, so the
  damage can reach a live session as subtly wrong metadata instead of an error. Use dashes or commas where
  a colon would go, or quote the whole value.
- The same validator enforces: `description` within 1024 characters with no angle brackets, `name`
  kebab-case within 64 characters with no leading or trailing hyphen, and only the keys `name`,
  `description`, `license`, `allowed-tools`, `metadata`, `compatibility`.

**Validate with two independent parsers, not one.** The consumer is Hermes, so check what Hermes sees:

```bash
# 1. structural validator (ships with the skill-creator skill)
python3 <...>/skill-creator/scripts/quick_validate.py <skill-dir>
# 2. Hermes's own frontmatter parse, which is what actually runs at load time
cd ~/.hermes/hermes-agent && env -u PYTHONPATH ./venv/bin/python -c \
  'import sys; sys.path.insert(0,"."); from agent.skill_utils import parse_frontmatter as p; \
   fm,_=p(open("<skill-dir>/SKILL.md",encoding="utf-8").read()); print(sorted(fm), len(fm["description"]))'
```

Expect exactly `['description', 'name']` and a plausible length. If a validator cannot import in the
ambient interpreter, run it with one that has the dependency — not with a wildcard venv glob.
`skill-creator` owns the eval/optimisation half of skill work (test prompts, benchmark, description
optimisation); this pack owns the Hermes-specific half.

## Pointers

- **Grep-verify every pointer before delivering.** A router whose references were renamed is broken even
  though every file exists. `scripts/verify-skill-package.py <skill-dir>` runs the whole lint — generated
  tree vs disk, plus pointers — stdlib only, exit 1 on any problem, so it is never done by eye or by a
  hand-typed grep.
- A pointer that leaves the package (a sibling skill, another repo's file) is written as a full path or
  `<sibling-skill>/<file>.md`; the lint resolves sibling names, and illustration-shaped names should read
  as shapes (`references/<topic>.md`), not as real filenames.
- **Lint section names and route labels too, not just paths.** Restructuring one reference — renaming its
  steps, re-labelling its routes — silently rots every sibling that cites them by name, and a path-only
  grep will not see it. After any restructure, grep the whole pack for the old labels and fix those
  citations in the same pass.

## Working in this repo

- **Look existing skills up by their bare name.** `skills_list` reports a `category` field, but that
  category is not part of the skill's name — the qualified `category/skill-name` form fails to resolve.
  Check for an umbrella that already covers the class before creating a new one, and read it in full
  before extending it.
- **Assume more than one writer.** Check `git status --short` and file mtimes before and after a batch of
  edits; a write can be refused as unread-since-modified, and the fix is to re-read once and retry, not to
  force it. If the diff is larger than your change, say which files you did not touch.
- **Regenerating a skill's tree encodes whatever is uncommitted inside it.** The generator renders every
  line count off the working tree, so regenerating a skill a sibling session is mid-edit in ships *their*
  uncommitted count inside *your* commit, and a fresh clone's `verify-skill-package.py` then fails against
  the pushed reference. Check `git status --short` for the skill you are about to regenerate; if it is
  dirty, hold both the tree and the row that needed it. Measured 2026-10-01: a route row for
  `install-hermes-skill-from-a-profile` would have carried a sibling's uncommitted 527→595 line count for
  `install-hermes-skills-from-github.md`, and was deferred until that commit landed.
- **A profile copy that is *ahead* of the clone is content the repo lacks, and `update --force` deletes
  exactly that.** Run `diff -rq <clone>/skills/<name> "$HERMES_HOME/skills/<install_path>"` immediately
  before any force; when the installed copy holds the newer text, backport it *mechanically* — match the
  block by a unique prefix, take the replacement's exact bytes from the copy so quoted measurements stay
  byte-identical — and commit the backport **before** forcing. Measured 2026-09-30: an installed
  `remove-hermes-skills/SKILL.md` carried a 9-line paragraph the clone did not (a session had edited the
  installed tree directly); the byte-exact backport committed first, and the force that followed left no
  drift. Name the foreign content in the report — never commit another writer's work silently.
- **A token-like string in a file is masked in tool output, so a literal replace silently misses.** Output
  renders secret-shaped text (a `$TOKEN` interpolation, an auth header) as `***`; an edit keyed on the
  string you were shown then matches nothing and reads as "the file already says something else". Confirm
  the real bytes through a channel that is not masked — base64 the line, check its `len()`, or match it
  with a regex over the raw file — and edit by pattern rather than by the displayed text.
- **Keep every probe surgical.** Scope a verification command to the artifact under test — one skill, one
  named lookup, one file — and never leave a repo-wide or unfiltered run in the foreground: a named lookup
  costs seconds where the sweep costs minutes, and a long silent command reads as the task hanging. That
  includes the generator's `--check` and `hermes skills check`, both of which have per-skill forms.

## Commit and report discipline

- **Scope questions go in ONE `clarify` call, recommended-first**: scope (body only / body plus every
  reference / body plus one named reference), body language, and what to do with a
  `<!-- Generated by Scripts -->` placeholder. The recommended answer for this user is body plus every
  reference — the half-filled shape is rejected.
- **Commit only when asked, in the order asked.** Stage a pathspec per commit (`git add <skill-dir>`); a
  concurrent writer's files may be sitting staged. Match the repo's message style: Conventional Commits
  with a Chinese subject (`docs(skills): …`). With no such request, do not commit on your own initiative —
  the exception is a request to *update a skill this repos delivers*: nothing reaches any profile until
  the change is pushed and re-installed, so commit → push `main` → reinstall is the task, not extra
  initiative, and the report says where it landed (ref or URL).
- **`git mv` stages what it moves, so a rename leaves the index dirty — and an unqualified commit
  swallows it.** After a rename, `git add <one-file> && git commit -F msg` commits *everything* already
  staged, and both subjects become false. Keep renames and their content edits in one pathspec-scoped
  commit and read it back (`git show --stat -M`) before pushing — the tree is the evidence
  (`git ls-tree --name-only HEAD:skills`), not the success line. A mixed split already pushed can be
  rebuilt (`git reset --soft <base>`, re-stage, re-commit, `git push --force-with-lease`), which is
  defensible only for your own minutes-old commits, and the report has to say you rewrote them.
- **Report with real numbers and the gaps.** `1) What I want  2) What I did  3) Effects of each change
  4) Things left to do`, with line counts and validator output, and an explicit list of what was **not**
  run — when the user says no further testing, say so plainly rather than implying the loop ran.
