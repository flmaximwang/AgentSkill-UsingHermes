# 跨账户配对去重与勾稽差排查

同一笔钱同时出现在银行流水和平台账单里是常态（提现、卡结算的平台消费、退款原路退回、合并付款）。
配对错了有两种后果，**都不能容忍**：漏配 → 同一笔记两遍；错配/断链 → 钱**凭空消失**、账户勾稽报差。

主流程（normalize/book/check/month/trend 的用法与交付口径）见 `accountancy-workflow`；
本 skill 只讲**配对与差数排查**这一块，两者配合看。

## 四条不可动的硬约束

1. **只有「钱确实从某张已导出的借记卡走」才允许配对**（`_funding_is_tracked`）：出资渠道要解析到
   **已导出的 1002 账户**。花呗/白条分分卡/信用卡付的、以及未导出流水的卡（工行/农行/网商等）扣的钱，
   银行对账单里根本没有这一笔；按同额去捞只会把平台侧那笔并进一条**不相干**的银行流水。
2. **一条银行流水只认领一条平台流水**（`used_in`/`used_out`/`used_platform`），同日并列再按时分秒就近。
   否则同额的多条平台流水全并进同一条，剩下拿不到说明的银行流水落进待分类。
3. **解不唯一就不配对** —— 错配比不配更糟，而且错配会以「断链」的形式把两层错误叠在一起，更难查。
4. **收紧永远比放宽安全**。放宽一处会在别的期间冒出新差；每次只改一处，**改完立刻重跑比差**。

## 方向判据：平台账单里的 neutral 是坑

平台账单把下面两类都标成 **neutral（不计收支）**，判据写成 `收支 == "out"`（或只认 `in`）会整批漏配：

| 平台侧字样 | 账单里的收支 | 它对应的银行侧 | 候选池 |
|---|---|---|---|
| `退款-XXX` / `<商户>-退款` | 常为 neutral | 「网上快捷退款」**流入** | `bank_in` |
| `余额宝/理财通-转出到银行卡`、`零钱提现` | neutral 或 in | 「银联入账/支付机构提现」**流入** | `bank_in`，**不是** `bank_out` |

漏配的后果都是两侧各记一次：平台侧按 `$settlement` 借了那张卡，银行侧的到账/退款也借同一张卡。

**实现要点（分支顺序）**：「回卡类」行（转出到银行卡、提现）必须排在「由银行卡结算 → `bank_out`」
那个分支**之前**先认掉 —— 否则它会被后者的关键词吸进 `out` 池里空找一场，永远配不上。

## 配对必须「同渠道」

支付宝的钱在银行流水里只会以「支付宝…」出现，微信/财付通的钱只会以「财付通…」出现。
不判渠道时，同额同日的错配会让**两条规则各跳过一侧**：

```
银行侧 B → 跳过，理由「与平台侧 P 配对，仅平台侧入账」
平台侧 P → 跳过，理由「与银行流水 B2 为同笔到账，保留银行侧」
```

B 的对手是 P，P 的对手却是不相干的 B2 —— **两颗棋子互指，谁都没真入账**，钱从账户里消失。
修法：`find_twin` / `_withdraw_twin` 的候选池先按渠道过滤（银行流水没写渠道字样时不拦，
否则摘要简写就配不上了）。

## 「一笔流水被两套规则争用」是同一种病

银行侧「转给本人另一张卡」的划转若被平台配对抢走，会被回填成「平台业务：…」、**摘要被改写**，
规则随之记错科目（本该「借对方卡/贷本卡」，却记成「借平台钱包/贷本卡」）；而另一端还以为它已入账
而被跳过 —— 两个账户都不对。修法：构建 `bank_in/bank_out` 时排除 `own_account_item()` 命中的行。

## 合并付款（一拖多）与组合支付

- **合并付款**：平台一次购物车结算拆成多笔订单明细，银行侧只有一笔扣款。要反向补一轮
  「银行侧一笔 ↔ 平台侧多笔合计相等」的子集和配对。组合笔数上限**别小于 8**（写 6 会静默放弃整组）；
  **退款行不参与**（同一笔钱既是支出又有退款时会出现两个解 → 整组放弃）；**解不唯一就放弃**。
- 配上后按用户的 **「粒度更细的为准」**：保留平台侧逐笔（带商品说明、账单类目、本人备注），
  跳过银行侧那一笔汇总。
- **组合支付**：结算方式形如「中国银行储蓄卡(xxxx)&支付宝小荷包(...)」= 卡 + 平台钱包，钱可能
  **全从平台钱包走**（银行流水里根本没有那笔扣款）。判据是**银行流水查无此笔**，不是关键词。
  注意「银行卡&立减金/红包/优惠」不是组合支付，那是优惠说明。

## 平台子账户（钱包 / 小荷包）的账户粒度

平台钱包、小荷包是**各自独立的池子**，账上要**按名字各立一个账户**（用户口径：「每个小荷包就是一个
账户」）；泛账户只留作「账单没写名字」时的兜底，明细名注明「未具名·兜底」。

⚠️ **不这么做的后果不只是明细难看**：出资渠道匹配取**最长关键词**，泛词「小荷包」（3 字）会输给
卡尾号「3572」（4 字）——「中国银行储蓄卡(3572)&支付宝小荷包(X)」这类写法的**出资方被判成卡**，
账户勾稽当场报差。按**全名**登记（全名总比尾号长）才是正解；别去改匹配算法本身，
最长优先还兼着「立减金 / 花呗金这类优惠词不许抢走出资渠道」的职责。

**遗留（数据本身缺失，不是实现问题）**：「卡 → 小荷包」的**充值**在银行摘要里**不写池子名**
（只写「支付宝-支付宝小荷包-转入」），所以充值端只能落兜底账户，而消费端落具体小荷包 ——
报表上会看到具体小荷包净流出、兜底净流入，**两边合起来才对**（勾稽仍是平的）。
补全只能靠人工映射（哪笔充值充的是哪个池子），银行侧没有这个数据；不要为了让报表好看去猜。

## 账户勾稽差怎么查（方法论：别从读代码开始）

差 = 记账净 − 流水净，逐账户必须为 0。**别拿「日期+金额」的缺/多清单当线索**：跨期或延迟入账的
同一笔（提现到账、退款晚一天入账）会**同时**报「缺」和「多」，而金额层面其实是平的 —— 照着它查
会被带偏。正确顺序：

1. **只看金额多重集（带方向）**：按 `Counter((金额, 收支))` 比「该账户该期的流水」与「借贷记到该账户
   的分录」，`booked - flow` = 记账多、`flow - booked` = 记账少，这两张清单直接给出净差的构成。
   分录取 `book(records, cfg, rules, coa, duplicates=dups)["entries"]` 的 `行`（含 `明细`/`借方金额`/
   `贷方金额`），别去解析 xlsx。现成脚本：`scripts/diff_amount_multiset.py <期间> <账户明细名>`
   （cwd = 项目根，绝对解释器 + 去 PYTHONPATH）—— 直接跑，别每次手敲。
2. **拿具体金额回原始流水查**：看那几笔的 `结算方式`、`收支`、账户、摘要。
3. **看它被谁跳过**：

   ```python
   res = book(records, cfg, rules, coa, duplicates=dups)
   skipmap = {(str(s.get("源文件")), str(s.get("源行号"))): str(s.get("_pair_skip") or s.get("_no_entry"))
              for s in res["skipped"]}
   # 目标流水：k = (源文件, 源行号)；在 skipmap 里就拿到**跳过原因原文**，不在就是入账了
   ```

   再确认「跳过它的理由」与「它声称的对手那笔的结局」是否自洽：对手若也被跳过，就是断链。
4. **一次只改一处，改完重跑逐期比差**：验证「没把对的配掉 / 没把错的配上」。

**反例（别重犯）**：用「存在某个未跳过的同额对手」当条件做自动修复 —— 同额记录满地都是，一跑就
误救上千笔（凭证 3,484 → 5,254，差 12 处 → 32 处）。收紧成「同日 + 同额 + 对手未跳过」也**没有**
验证过能跑通：那种「存在性」判据天生分不清「这笔该由我对家入账」与「另一笔碰巧同额」。
**修正则，不加兜底** —— 顺着 `_pair_skip` 找到判据错的那条规则改对，断链才会真正消失（本 skill 后面
几张表里的根因全是从「跳过的对手为何也跳过了」追出来的）。

## 银行「余额」列：逐笔余额链自检（查「报差但账是对的」）

勾稽报差时先分清是**账记错了**还是**取数取错了**。银行流水自带余额列，可以做一条**解析层**的独立验算
（比文件自带的笔数/收支合计锚点更强 —— 锚点对得上仍可能「少解析一笔 + 多解析一笔」或方向记反）：

```
余额_i − 余额_{i−1} == ±金额_i     # 逐笔成立；断点 0 才算解析可信
```

- **同一秒内多笔**（中行出现过 2 组）先后不可知 → 组内按贪心找一条能走通的顺序，**互换不算断点**，
  否则会报一堆假断点。
- 余额链通了就能推**期初**：`首笔余额 − 该笔金额`（＝该笔之前的余额，即该期期初）。这是唯一能从
  流水取到的期初；平台/投资账户没有余额列，只能外部录入。
- **期末余额 = ≤ 期末 23:59:59 的最后一笔带余额流水**（本期无发生额就自然结转上一期）。

**排序陷阱（会造成假差额）**：中行流水**同一天的明细在 PDF 里是倒序**（最新在前）。只按日期排序时
同日多笔的先后由文件顺序决定 → 「当日/期末最后一笔」取到的是当天**最早**那笔的余额，实测伪造出
11 处假差（其中一个 4,450.00，且相邻两期符号相反、看着像「记错了月份」）。**必须按完整时间戳排序**
（14 位 YYYYMMDDHHMMSS，缺时间补 0；建行只有日期，退回 00:00:00 保持先到先得）。

## 字段被静默丢弃：查「这列到底进没进来」

解析器只把**映射过的列**组装进记录：`REC_COLUMNS` 与 `record_from_cells` 里没有的字段，记录和中间表
里都看不到（中间表的列就是 `REC_COLUMNS`）。曾因此让账单的「备注」列整个消失，任何按备注判定的
规则**永远不命中且不报错**。查字段是否存在要直接看 `record` 的键，别只看中间表。
新增一个可判定字段 = `REC_COLUMNS` + `record_from_cells` + 档案 `columns` 三处都加。

## 不要试图回写银行 PDF

银行侧是 **PDF → 中间表 CSV → 借贷记账的单向链路，不回写、不在 PDF 上留更正**（用户明确）。
若要用「配对 UID」写死配对关系，只能写在平台侧（CSV/XLSX 的备注列），用「同 UID 各笔的合计」去
指定银行侧对手，且**解不唯一就不动手**。注意解析平台侧记录的「出资账户」必须用 `_settlement_account()`
—— `_money_account` 是平台账户本身，拿它去跟银行侧比永远不相等，机制会静默失效（UID 全都「未生效」）。
