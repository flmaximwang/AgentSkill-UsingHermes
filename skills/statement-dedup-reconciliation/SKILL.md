# 多源流水的配对去重与账户勾稽

同一笔钱常在两份账单里各出现一次（平台提现 ↔ 银行入账；平台消费由卡结算 ↔ 银行扣款；
自有账户互转的两端；京东回单 ↔ 账单 ↔ 银行）。配对做错有两种后果，都会让账失真：

- **配错**：两条不相干的流水被并成一笔 → 一侧拿不到说明、落进待分类或记错科目；
- **漏配 / 断链**：两侧各记一次（虚增资金与费用），或**两头都跳过**（钱凭空消失）。

**账户勾稽是唯一的判决书**：对每个银行账户，
`流水净变动 == 记账净变动 + 本期待分类金额`，逐分相等。不为 0 就是有笔钱被跳过却没在别处入账。

代码位置：`Scripts/books.py` 的 `pair_by_uid → pair_jd_duplicates → pair_internal_transfers
→ pair_card_funded → pair_own_account_transfers → pair_credit_card_repayments`
（**顺序有意义**，见下）。

「资金侧」不只借记卡：**信用卡账单（来源 `boc_credit`）也是资金侧** —— 模块常量
`_CARD_SIDE = ("bank", "boc_credit")` 用在 `pair_card_funded` 的两个池子与 `tracked` 上，
`_funding_is_tracked` 允许 `code in ("1002", "2241")`。接入信用卡账单之前 `_CARD_SIDE` 只有 `bank`
（那时把信用卡消费配进借记卡流水是错的，见 `_funding_is_tracked` 的注释）；接入后平台侧
「结算方式＝某信用卡」的消费/退款才**有对手可配**。**新接入一个信用卡来源，第一件事就是改这两处**
（池子 + 科目码白名单），否则平台侧那些行会与账单侧各记一次（重复入账）。

## 一、先诊断，别先改

1. **用纯金额多重集比对，不要用「日期 + 金额」。** 跨日期的同笔（提现到账、退款延迟入账）在
   「日期+金额」口径下会**同时报「缺」和「多」**，看着像两处问题、其实金额层面是平的 ——
   按那个线索追会追错方向。
   ```
   flow   = 该账户该期的流水  -> Counter{(金额, 方向)}
   booked = 该账户该期的分录  -> Counter{(金额, +借方 / -贷方)}
   extra  = booked - flow   # 记账多
   miss   = flow - booked   # 记账少
   ```
   净差 = 多 − 少。
2. 对可疑流水，**打印它在哪一步被跳过、`_pair_skip` 原文是什么** —— 比读代码猜快得多。
3. 遇到查不动的金额先排除「合并付款」：银行侧一笔 == 平台侧 N 笔之和（两侧金额相等、日期也同）
   → 不是问题。
4. **「重复流水」护栏也会静默丢真实流水**：`book` 对「同一交易单号重复出现」是**记问题并跳过**。
   若某来源的单号是用字段拼的（日期+商户+金额），**同日、同商户、同额的两笔（真实存在）会被当成重复
   丢掉一笔**。诊断：`配对与问题` 表里出现「重复流水（交易单号 …）：<文件> 第 N 行，已跳过」就是它。
   修法：单号**逐行唯一**（把行号/序号拼进去）。**别指望对账锚点能发现** —— 锚点比的是合计，
   少一笔多一笔照样平（实测静默丢 5 笔）。

详细对照表与诊断脚本见 `references/pairing-dedup.md`。

## 二、五类已确证的根因（按此顺序查）

| 症状 | 根因 | 修法 |
|---|---|---|
| 平台侧「退款-…」两侧各记一次 | 退款配对只认 `收支 == "in"`，而账单把退款标成 `neutral`（不计收支） | 放宽成 `in ("in", "neutral")` |
| 平台侧提现/退出行配到了**另一家渠道**的银行流水 | 只按同额+同日配，没有渠道约束 | 配对前按「支付宝↔支付宝、财付通/微信↔微信」过滤；银行侧没写渠道字样时不拦 |
| 银行侧「转给本人另一张卡」的划转被平台配对抢走 | 它进了 `bank_in` / `bank_out` 池，被回填摘要后规则下错科目 | 建池时排掉 `own_account_item()` 命中的行 |
| 平台侧「转出到银行卡」（neutral）永远配不上 | 只去 `bank_out` 找对手，而它是**流入** | 该分支去 `bank_in` 找 |
| 两头都跳过、钱凭空消失（断链） | 配对规则各跑一遍、互相看不见对方跳了什么 | 收紧各自条件；**不要**加「找不到对手就救回来」的兜底 |

两个「判不出」而非「配错」的：

- **合并付款的笔数上限**：一笔银行扣款可以对应平台侧 **8 笔**订单明细；子集和搜索的 `max_items`
  写小了会**静默放弃**整组（银行侧与平台侧各记一次）。放宽到 12。
- **退款行不能进合并付款的组合**：一笔支出与它的退款同额同日，会让组合出现第二个解，触发
  「解唯一」判据放弃整组。构建候选时排掉摘要含「退款」的行。

## 二之二、信用卡账单侧的「假差额」与对手方识别

信用卡账单的「存入」列混着**还款 / 平台退款 / 美元购汇**，按交易描述分不开；
把非还款当成还款去资金侧找对手，就会得出「还款对不上账单」的假结论（为这个绕过一大圈）。
卡勾稽/账单对不上时**先排除这三种假象**：

- **退款回卡**：账单「存入」里的 `支付宝CHN` / `（特约）…CHN` 可能是平台**退款**（平台侧有同额的
  「交易关闭 / 退款成功」兄弟行，结算方式写着本卡）→ 按退款冲减原费用，别当还款。
- **美元购汇还款**：美元段的「存入」＝ 借记卡出的**人民币**，同日、按隐含汇率折算
  （已核验：`23.00 美元 ↔ 3358 出 157.58`、`98.81 美元 ↔ 3358 出 668.25`）→ 别去追一笔
  不存在的人民币还款；闭合校验 `Σ美元支出 − Σ美元存入 = 该期美元欠款`。
  外币消费本身怎么入人民币账（简化折算 vs 单列 `5603 财务费用—汇兑损益`）见 `credit-instrument-balances`。
- **支付宝红包**：卡侧「存入」比资金侧转出多几元（`2,098.66` ↔ `2,097.76`），差额是红包 ——
  支付宝那笔的「收/付款方式」写着 `中国银行储蓄卡(3358)&红包` → 配对按**资金侧金额**，不要当成配不上。
  差额**单独记一对借贷**（用户口径：分开记，不合成一笔）：借 负债 ｜贷 `5301 营业外收入—返现/优惠`；
  它没有对应流水 → 写进 `Config/adjustments.yaml` 的**手写条目**，**id 前缀别撞 `调-<期间>-市值-`**
  （那个前缀会被 `balances --adjustments` 按 id 幂等覆盖），`依据` 里写清凭据（哪张 App 截图 + 算式）。

对手方识别：**`2088…0156` = 支付宝支付科技有限公司**（银联渠道账号尾号，如
`20886220676450310156` / `20882221166926340156` / `20884436797924320156`）—— 在借记卡侧表现为
「银联入账｜支付宝款项」（全是收钱方向），在信用卡侧表现为还款的对方账号；
**它不是某个未导出的支付宝个人账户**，别把配不上的还款挂到「另一个支付宝」上。

**账单链校验（最快的诊断）**：信用卡账单的**每期「上期余额」必须等于上一期「本期余额」**。
缺某一期账单时，直接用下一期的「上期」把缺口读出来（比翻流水快），也拿它验解析对不对。

## 二之三、信用卡账单的还款侧与分期：谁入账、谁跳过

- **还款存入行 ↔ 资金侧还款转出**（`pair_credit_card_repayments`）：账单侧的
  `BOCNET` / `还款成功 , 谢谢 !` / `无法足额扣款，请补足账户余额` / `支付宝支付科技有限公司`
  与资金侧（借记卡转出、平台「信用卡还款」）按**金额 ±1.00 + 日期 ±5 天**配对，
  **保留资金侧、跳过账单侧**（同一笔还款别两边各记一次）。±1.00 是为红包抵付那类留的（见上）。
  **只认还款类存入行** —— 分期「冲销原交易金额」、退款、财政贴息各有各的分录，别在这里配掉。
  配不上的账单侧还款＝钱来自没有流水的账户 → 留待分类，不猜。
- **分期必须成对处理**：`…冲销原交易金额`（存入）要贷回**原交易那条费用明细**，同期
  `<00x/00y>…分期`（支出）是重记的本金、`分期利息` 才是真成本。规则没法动态取明细 →
  先把冲销行与**同额原交易行**（同文件、更早交易日）配对、把原行摘要/账单类目抄进冲销行，
  再按类目写一组冲销规则（类目→明细）；直接共用一个兜底明细会让分类偏 ——
  原消费留在原类目，兜底明细上出现一笔大额负数。

## 三、断链：一种会静默吞钱的机制

```
银行侧 B（提现到账）   ← 被 pair_internal_transfers 跳过，理由「平台侧 P 会入账」
平台侧 P（小荷包-转出）← 被 pair_card_funded 跳过，理由「另一笔银行流水会入账」
```

B 的对手是 P、P 的对手是另一个人 —— **谁都没入账**。本例的判据就是「渠道不一致」：
P 是支付宝的行，却配到了银行侧写着「财付通」的那笔。

**修法是收紧条件，不是补一个「断链修复」兜底。** 曾写过「跳过的记录若找不到未跳过的同额对手，
就放回来入账」—— 判据太宽（银行流水里同额记录本来就多），一次运行误救 1,770 笔，
凭证数翻倍、勾稽差从 12 处变 32 处，比不修更糟，只能回退。

## 四、修复纪律：只准收紧，一处一根因

1. 一处只改**一个**条件；
2. 改完**立刻重跑**，记下差数变化；
3. 差数**只减不增**才算修对；变差就回退这一处；
4. 同一类差可能分散在多期 —— 看全部期间的差数，不只看当期的。

## 五、出资方判错 = 另一类勾稽差

「这笔钱到底从哪走」判错，贷方就挂到错误的账户上，账户勾稽同样报差。

- **`settlement_accounts` 取最长关键词**（同长才按表序）。**泛词会输给卡尾号**：
  「小荷包」（3 字）比尾号「3572」（4 字）短 → 「中国银行储蓄卡(3572)&小荷包(…)」被判成卡。
  子账户（小荷包等）要**按全名**登记映射，全名自然比尾号长。
- **「卡&小荷包」写的是资金来源链**（卡 → 充进小荷包 → 从小荷包付给商户），**不是**组合支付。
  真正扣款只发生在小荷包，卡那一步是另一笔单独的「小荷包-转入」。**不要去拆 X+Y**，
  也不要凭「账单上写了卡」就补一笔卡的分录 —— 卡上没有这笔扣款，补了就是凑数。
- **子账户各立一个明细**（每个小荷包一个账户）；合成一个泛明细会让出资方判错、池子也看不清。
  规则里的资金方用 `$keyword` 按名字定位，**不写死泛账户**，否则一头净流入、一头净流出。
- **新增科目码要同步两处**：`stats.py`（`BLOCK_OF` / `ASSET_CODES` / 报表块的逐科目列示）与
  `trend.py`（`ROW_OF` / `REQUIRED` / 资产合计构成式）。漏了会报「科目码未归类」
  或「资产合计对不上」，或更静默地留下恒等式残差。

## 六、交付前的闸门

- 逐账户银行勾稽**全部「一致」**（账本「配对与问题」表）；
- 统计表的两条勾稽都为 0：①资产 − 负债 − 权益 ②现金净增加额 − 货币资金净变动；
  **两套都要看** —— 只看统计表就宣称「勾稽全为 0」是不够的；
- 待分类为 0（或逐条说明为什么留着）；
- `check --workbook <账本>` 结论「通过」；
- 凭证张数/借贷合计与上次不同时，**能说出为什么**（配对跳过条数变化属正常）。

## 与用户协作的纪律

- **口径有多种选法时，先给「候选方案 + 对数字的影响」，等确认再动账。** 不要先改完再解释。
  他选定后会说「继续做」—— 那时把余下的条目一次做完，别回头再确认已经定过的事。
- **对不上的还款，让他发卡片 App 的「明细」截图** —— 那页带**对方账号**（如 `2088******0156`）与
  对方户名，比账单 PDF 多一列，一步就能定位资金来源（账单侧的交易描述只写 `BOCNET`/`支付宝CHN`）。
- **把「流水事实」和「我的推断」分开说**：能确证的（银行侧确实没有这笔扣款）与推出来的
  （所以钱是从小荷包走的）要标清楚，并给出核实途径（账单里的支付详情 / 银行 App 明细）。
  把推断当事实讲会被追问，也会把人带偏。
- **不猜**：认不出对方账户、认不出出资渠道就报错停下，不许兜到笼统科目或默认某张卡。
- 银行侧是**单向链路**（PDF → 中间表 CSV → 借贷记账），不回写、不在 PDF 上留更正 ——
  不要提「往 PDF 写备注」这类方案；要带标记就带在平台侧账单（CSV/XLSX）的备注列上。
