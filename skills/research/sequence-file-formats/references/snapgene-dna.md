# SnapGene `.dna`: container layout + measured write-path audit

## Container (Verified by an independent TLV walk, not by a library)

19-byte header, then repeating blocks of `1-byte type || 4-byte big-endian length || payload`:

| offset | size | value |
|---|---|---|
| 0 | 1 | `0x09` (`\t`) magic |
| 1 | 4 | `0x0000000E` header length |
| 5 | 8 | `SnapGene` |
| 13 | 2 | type_of_sequence (1 DNA, 2 protein, 7 RNA) |
| 15 | 2 | export_version |
| 17 | 2 | import_version |

Walking from offset 19 with `seek()` over each payload consumes the file exactly (`trailing
bytes = 0` on every real file tested) and scans a 1296-file / ~550 MB vault in **4.1 s** —
this is the cheap way to inventory a whole library read-only.

Payload encodings: 0 UTF-8 DNA · 1 2-bit packed DNA · 5 primers XML · 6 notes XML · 7 history
tree XML (LZMA at v15+) · 8 sequence properties XML · 10 features XML · 11 history nodes
binary+TLV · 14 custom enzyme sets XML · 16 trace container · 17 alignable sequences XML ·
18 ZTR trace · 20 strand colours XML · 21 protein · 23 attachments · 27 trace alignment
(BGZF+BAM) · 28 enzyme visibilities XML · 29/30 history modifier/content · 32 RNA · 34 RNA
structure · 2/3/13/35 vendor-generated caches. ~92% of bytes are printable ASCII because the
XML blocks are inline — that is why `cat -v` looks like an invitation to hand-edit. It is not;
the length prefixes are binary.

## The audit: four layers, and which ones pass

Toolchain: `sgffp` 0.22.x (PyPI, MIT, reverse-engineered; claims parity with SnapGene **8.2.2**;
the installed app here is **8.2.1**). Test corpus: the user's own 1296 real `.dna` files.

| layer | verdict | measured evidence |
|---|---|---|
| content (what SnapGene shows) | **lossless** | 20/20 random real files parsed + wrote back with 0 errors and no structural loss; 8 deep-compared: sequence, topology, features *including qualifiers*, primers, notes all IDENTICAL; cloning-history tree identical 6/6 (4–36 nodes) |
| byte | **not preserved** | `sha256` differs on **20/20** even with `preserve=True` — XML is re-serialised through `xmltodict`; per-block deltas: features +1.3%, notes +2.9%, primers −0.0%, enzyme sets −2.4%, strand colours −2.0%, history nodes −5.0%…+0.1% |
| version / legacy | **as documented** | a v13 file keeps blocks 2/3/13 verbatim and `export_version` stays 13 →13; v15 files lose 3/13 by design (SnapGene regenerates them) |
| forward compatibility | **FAILS** | `parse_blocks` skips any type not in the scheme with only `logger.debug` + `continue`; injected synthetic block type 55 is flagged `[NEW]` by `sff check -l` and dumped by `sff check -d`, yet the reader never stores it and a write-back deletes it. No raw/unknown retention API exists. |

Consequence for a daily SnapGene user: a release that adds or re-encodes a block type silently
drops it from any file that goes through a read→write cycle.

## The `[*]` trap (the most expensive finding)

`sff check -l` marks blocks it knows as `[*] undecoded but known blocks (auto-generated by
SnapGene)`. That marker comes from a **different set** than the reader/writer uses:

- `cli.py`: `UNDECODED_BLOCKS = {2, 3, 13, 35}`
- `parsers.py`: `LEGACY_CACHE_BLOCKS = (2, 3, 13)` (and 35 is absent from `SCHEME` too)

So on a real file: `check` reports block 35 as known-safe, and write-back yields
`LOST ON WRITE: [3, 13, 35]`. **Treat `[*]` as "the check command knows it", never as "the
writer keeps it"** — verify the id against the module the reader/writer actually consults.

## Gate before any `.dna` write

1. `sff check FILE -l`; any `[NEW]` → do not write.
2. Cross-check every `[*]` id against `SCHEME` / `LEGACY_CACHE_BLOCKS` (see `scripts/scan_dna_blocks.py`).
3. Never overwrite the source `.dna`; write to a new path.
4. Default to `sgffp` as a **read-only exporter** (`.dna` → GenBank/JSON for agent use, batch search, annotation diffing) and keep writes in SnapGene itself.

## The only non-circular acceptance test

Re-reading `sgffp`'s output with `sgffp` proves nothing about SnapGene. SnapGene.app is
installed here (8.2.1), so the decisive test is manual: open the rewritten file in SnapGene →
check the map, feature/primer panels and history tree → save → rescan the blocks: caches
3/13/35 reappearing proves they were regenerable. Offer this test; never claim vendor
verification that was not run.

## Comparing two `.dna` files (and deciding whether one is redundant)

Byte equality is the wrong test, and offset diffs are actively misleading.

- **Circular origin shift.** Two files can hold the same molecule with different numbering starts:
equal length, one a rotation of the other (`shift = (sa + sa).find(sb)`, topology stays
  `circular`). Treat that as the same sequence. Then note that comparing feature lists by
  absolute coordinates flags **every** feature as different — shift the second file's coords
  `(start + shift) % L` first. Measured: a pair matched on all 16 features only after the shift.
- **Compare block multisets, never offsets.** SnapGene reorders blocks, and LZMA-compressed
  history avalanches, so an offset diff can report six figures of "difference" for two files
  that share every byte of payload. Walk both files and compare
  `Counter((block_type, sha256(payload)))`; report the type-level diff, not a byte count.
- **What a genuinely "different" pair differs in.** Mostly block 13/2/3/35 (vendor caches —
  regenerable; they account for the 1–76-byte deltas), then re-serialised features/primers/notes
  XML (identical semantics, different writing, e.g. 37 B), and only sometimes real user data
  (block 11 history nodes, 16 traces).
- **"Is this file preserved elsewhere?" → union over ALL candidate copies, not the closest one.**
  Read each candidate with `snapgene_file_to_dict` (features + qualifiers, notes) and
  `snapgene_file_to_record` (sequence), rotation-align, then union the feature sets and the
  `(block type, payload hash)` sets. Report only what no copy carries. Real outcome: one file's
  26 traces lived in the same-folder twin while its 135 history nodes lived in a `Records/`
  copy — no single equivalent file, but nothing lost.
- **For a deletion decision, report the layer.** Which copy, which layer (sequence / features /
  primers / notes / traces / history / regenerable cache), and the byte counts — "bytes differ"
  is not an answer.
