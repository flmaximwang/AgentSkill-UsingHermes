# 支付宝交易明细（CSV）

- 账户 / 资金科目：`支付宝余额-15857617226` → `accounts.alipay`（1012 其他货币资金）
  - 小荷包相关流水 → `accounts.alipay_piggy`（1012 其他货币资金—支付宝小荷包）
- 档案：`config/bank_profiles.yaml` → `profiles.支付宝`
- 样例文件：`~/Downloads/流水/支付宝/支付宝交易明细(20260801-20260831).csv`
- 导出账号：`7226`（档案 `accounts["7226"]`，内容证据 = 说明块「支付宝账户：15857617226」）

## 文件形态

- **编码 GB18030**（`file -I` 显示 unknown-8bit，强行按 UTF-8 读会乱码）。
- 前面是说明块（导出信息、姓名、账户、起止时间、共N笔记录、收入/支出/不计收支统计、特别提示 1-8 条），
  然后是分隔线 `------------------------支付宝支付科技有限公司  电子客户回单------------------------`，
  再下一行才是表头。**表头行号不固定，用「交易时间,交易分类,交易对方」定位**（样例在第 24 行）。
- 12 列：

```
交易时间 | 交易分类 | 交易对方 | 对方账号 | 商品说明 | 收/支 | 金额 | 收/付款方式 | 交易状态 | 交易订单号 | 商家订单号 | 备注
```

## 解析要点（踩过的坑）

1. **金额无符号**，方向看「收/支」：`收入` / `支出` / `不计收支`（不计收支 = 内部转存、提现、理财等）。
2. **0.00 元流水真实存在**（样例有 1 笔 0.00 元支出）。它计入文件笔数，因此解析必须保留该行
   （否则对不上笔数），但**不生成凭证**。
3. 交易订单号 / 商家订单号字段**尾部带 Tab**，必须 strip，否则去重和关联都会失效。
4. `收/付款方式` 是关键信息：写着「中国银行储蓄卡(3358)」表示这笔钱的真实出处是银行卡，
   **银行流水里会出现同一笔**，必须去重（见下）。
5. 文件自带的「收入/支出/不计收支」统计与明细逐笔累加**可能不一致**（文件自己声明
   「因统计逻辑不同…请以实际交易金额为准」）。以明细逐笔累加为准，并在报告里同时列出两者差值。

## 与银行流水的去重（重要）

- 平台**支出**且结算方式是**已导出的借记卡**（中行 3358 / 建行 2464）→ 保留银行侧，平台侧跳过，
  并把商品说明回填到银行侧摘要；
- **只有钱真从已导出的借记卡走才配对**：花呗 / 白条分分卡（南京银行）/ 信用卡 9393・5235・0270，
  以及**未导出流水**的卡（工行 8935、网商 0026、农行 4077、广发 0675）付的消费，银行对账单里
  根本没有这一笔 —— 按同额去银行流水里捞，只会把平台侧那笔并进一条不相干的银行流水。
  这类行由平台侧自己入账，贷方记对应的信用工具/卡账户。
- 一条银行流水**只认领一条**平台流水，同日并列时按**时分秒**就近（否则同额多条平台流水全并进
  同一条银行流水，其余银行流水会拿着光秃秃的摘要落进待分类）。
- 基金/理财「卖出至银行卡」：银行侧才是到账凭据（「银联入账｜蚂蚁基金赎回到银行卡」）→ 保留银行侧。
- 支付宝账单里同一笔往往**与银行流水的秒数只差 1 秒**（账单 11:03:26 ↔ 银行 11:03:27），
  这是「同一笔钱两条记录」的天然指纹，比只看日期可靠得多。
（实现见 `books.pair_card_funded`，跳过的每一笔都会写进凭证表的「配对与问题」工作表。）

## 「交易分类」是可用字段（按类目归类）

`交易分类` 与 `商品说明` 一起拼进中间表的「摘要」（`商品说明｜交易分类`），因此规则里用
`summary_any: ["｜服饰装扮"]` 就能**锚定类目那一段**，避免商品名里恰好出现同样字样时误命中。
类目规则优先级放在具体商户规则之下（73 < 餐饮/交通/医疗/数字服务/软件/日用百货/平台购物）。

> 坑：退款判据不要写成 `summary_not_any: ["退款"]` —— 商家的政策文案里有「不退款」
> （如「如有疑问联系平台客服…不退款｜服饰装扮」、扫码点单小程序的「不支持退款」），
> 会把真实消费整批挡在所有消费规则之外、落进待分类。写成 `["｜退款", "退款-"]`。

## 科目转换（该账户常见交易）

| 交易分类 / 摘要 | 分录 |
|---|---|
| 小荷包-自动攒、小荷包-转入（支出） | 借 其他货币资金—支付宝小荷包；贷 其他货币资金—支付宝 |
| 小荷包-转出（收入，不带银行卡） | 借 其他货币资金—支付宝余额；贷 其他货币资金—支付宝小荷包 |
| 小荷包-转出到银行卡（收入，与银行配对后） | 借 银行存款；贷 其他货币资金—支付宝小荷包 |
| 提现到银行卡 | 借 银行存款 + 借 财务费用—手续费；贷 其他货币资金—支付宝 |
| 小荷包内「转圈/减肥/漂流/露营」计划进出 | 内部划转（同上口径），不进费用 |
| 交通（公共交通卡随用随充、哈啰） | 借 管理费用—生活支出-交通；贷 结算卡账户 |
| 餐饮（堂食、小吃等） | 借 管理费用—生活支出-餐饮；贷 结算卡账户 |
| 生鲜（叮咚买菜、盒马）且标为不计收支 | 待分类（不计收支往往表示资金另有来源，需人工确认后再定） |
| DeepSeek-API、云服务、订阅类 | 待分类（个人/经营用途需人工区分） |

## 跨期导出按月拆分（`split`）

一次导出多个月（如 `支付宝交易明细(20260101-20260731).csv`）时先拆再入库：

```bash
cd /Users/maxim/Documents/Obsidian/wangfanlin4_Accountancy
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts split "<文件>" [--dry-run] [--force]
```

- 产物落 `Running Account/支付宝/支付宝_7226_YYYYMMDD_YYYYMMDD.csv`（GB18030，沿用原行结束符：
  说明块 = CRLF、明细 = LF；`交易订单号/商家订单号` 尾部的 Tab 原样保留，解析时会 strip）。
- 说明块保留，但「共N笔/收入/支出/不计收支」按**该月明细逐笔累加**重算，并加一行「拆分说明」记出处。
- 多期原件必须留在 `Running Account/` 之外：全期文件 + 按月文件同时存在会被 `normalize` 各解析一遍
  而重复入账；`split` 对位于该目录内的源文件直接拒绝（不要用 `--force` 绕过）。
- 按行拆分要求字段内无换行（本账户导出满足）；若 csv 行数 ≠ 文本行数，`split` 报错而不是硬拆。
