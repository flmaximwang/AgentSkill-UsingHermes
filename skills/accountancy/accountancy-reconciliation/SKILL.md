# 账户勾稽差与配对修复

端到端流程（normalize → book → check → 交付）在 `accountancy-workflow`；**本 skill 只管「配对与问题」
表报出来的账户勾稽差**（`勾稽[YYYY-MM] <账户>：不一致，差 X`），以及改动 `books.pair_*` 时的纪律。

## 铁律

1. **先立回归指标**：`book 2>&1 | grep -cE '不一致'` 的数字就是基线。一次只改一条规则，改完必跑；
   数字变大就是回归，**立刻回退**再分析，不要带着更大的差继续往前改。
2. **只收紧，不放宽**。放宽判据的代价实测过：把「跳过的记录只要还能找到未跳过的同额对手就算有人
   代表」当兜底修复，一次运行多认 1,770 笔（凭证 3,484 → 5,254），差从 12 处炸到 32 处 ——
   银行流水里同额记录遍地都是，按同额扫全表必然误伤。
3. **先预测再跑**：动手前算出「这处差改完应该是多少」，跑完对不上说明还牵动了别处；对得上才算钉住。
4. **诊断用两套口径**：带日期的多重集差集（看哪一天缺什么）＋**纯金额**多重集（跨日期不干扰）。
   跨日期的同一笔（提现到账、退款延迟入账）在带日期口径里会同时报「缺」和「多」，而金额层面其实是平的
   —— 拿它当差的成因会把人带偏。
5. **两套勾稽都要看**：`统计` 表里的「资产−负债−权益」「现金净增加额−货币资金净变动」只证明表内自洽；
   逐账户银行勾稽在「配对与问题」表。交付前逐期把银行行扫一遍（须为「一致」）。
6. 修完必看：① 不一致处数下降 ② 每期 `check` 仍「通过」③ 待分类仍为 0
   ④ 发生变化的「配对跳过」条数都能在「配对与问题」表里解释。

根因清单、诊断脚本要点、UID 显式配对的完整做法见 `references/账户勾稽差排查.md`。

## 勾稽为 0 ≠ 账对：科目被规则抢单是最安静的错

**自有账户划转的 `own-account-move` 的 priority 必须高于一切分类/消费兜底规则**（现设 80 >
`category-other` 的 73）：对方账号已登记在 `own_accounts` 里就**只可能是划转、不可能是消费**。
优先级低了，摘要带「｜其他」的还款（「转账支出｜----------｜其他」）会被分类兜底规则抢走记成
「生活支出-其他」→ **费用虚增、负债少记**，而**银行逐账户勾稽与两道报表勾稽照样全为 0**（错的只是
科目）—— 只能靠「负债明细出现借方余额」或「信用卡账单核对」发现（实测 5 笔 2,038.24）。

排查顺序（负债/费用对不上但所有勾稽都为 0 时走这条）：① 回看该明细的凭证里有没有「本不该在这里」
的费用/收入行 ② 把 `own_accounts` 登记的对方账号与凭证贷方账户逐个对 ③ 再看规则 priority 表
（分类兜底规则的 priority 是否越过了专项规则）。

## 银行侧的第二重证据：余额链自检（别只信文件自带锚点）

银行流水自带「余额」列，可以逐笔验算 **`余额_i − 余额_{i−1} == ±金额_i`**（收支 in/out 定符号）。
它比「文件自带的笔数 / 收支合计」锚点更强：**锚点对得上仍可能「少解析一笔 + 多解析一笔」或方向记反**，
余额链对不上就是解析错了。`python -m Scripts balances` 顺带跑它（断点会列出处），
另外用「≤ 期末 23:59:59 的最后一笔余额」当期末余额、与账本逐期对 `上期余额 + 本期净变动 = 本期余额`。

- **取「某日/某期最后一笔」必须按完整时间戳排序，不能只按日期**：中行同一天的明细在 PDF 里是**倒序**
  （最新的在前），只按日期排序时同日多笔的先后由文件顺序决定 → 会取到当天**最早**那笔的余额，
  伪造出一整批「银行勾稽差额」（实测 11 处、其中一个 4,450.00）。**这类假差额比不报更糟**：
  以后真丢账就没人信了。排序键用 14 位 `YYYYMMDDHHMMSS`（建行只有日期 → 补 0，先到先得）。
- **同一秒内多笔**（中行流水里出现过）先后不可知：组内找一条能走通的顺序即可，**组内互换不算断点**，
  否则会报出一批永远查不出的断点。
- 期初也能从流水首笔推：`首笔余额 − 该笔金额`（只在最早有记录那一期用）—— 有了它，最早一期也能勾稽，
  而不是一句「首期锚点」带过。

## 信用卡/信用工具的余额勾稽（外部账单 vs 账本）

- 信用卡**没有月末余额可读**（账单日各卡不同：中信 0270 每月 16 日、中行 9393 每月 14 日），
  欠款由 `Asset Balance/信用卡账单.tsv`（人工维护）＋账本滚动推导，
`python -m Scripts balances` 逐期打出三个口径（设期末 D、最后一张已出账单日 B）：

| 口径 | 公式 | 含义 |
|---|---|---|
| 账单口径 | Σ账单(≤D) − Σ账本借方(≤D) | 已出账未还 |
| **综合口径（资产表用这个）** | 账单口径 + Σ账本贷方(B, D] | 已出账未还 + 未出账消费 |
| 账本口径 | Σ账本贷方(≤D) − Σ账本借方(≤D)，期初 0 | 流水能看到的欠款 |
| **账单未覆盖** | 账单口径 − 账本口径 | **账单里有、我们流水里没有的消费** |

- **「账单未覆盖」是本工具唯一能发现「某张卡的消费被漏记」的手段**：中行 9393 在 2026-08-31 有
  **3,344.68** 只出现在账单里（6~8 月逐月扩大）→ 账本的**费用与负债同时少记**这么多。发现后报给用户
  定夺（线下刷卡 / 美元子余额 / 分期，类目不明 → 不猜，先只报差额）。
- ⚠ **加「未出账消费」时只加贷方**：借方（还款/退款）已在账单口径里减过一次，按 `贷 − 借` 再加一遍
  就是重复扣，早期期间会算出**负欠款**（假差额）。
- **能读到「未还余额」的卡就用人工值，推导值只当对照**：该卡还款/消费有缺失时推导必然偏高
  （9393：账单合计比流水里能找到的还款多约 2,700 → 推导 2,435.07，用户实际未还 1,022.23 + 美元 20）。
  人工值按用户说清的时点落期间（他说「现在」就落当前期），美元**单列不换算**（无汇率凭据）；
  人工录了余额的卡不再用推导值，否则同一张卡两个数并存。
- 账单口径与账本口径**都不能单独当余额**：前者系统性少算未出账那段，后者漏掉没进流水的消费。
- 周期消费合计与账单**不会完全相等**（差几十元）：卡的记账日与平台交易日差 1–2 天、个别笔跨了周期
  边界 —— 不要为凑平去改周期定义；**上千元的差才是漏记**。
- 校验靠两个事实：① 还款额 = 上一张账单（0270：7/3 还 1,860.79、8/4 还 2,057.43，一分不差）
  ② 第一张账单 ≈ 该周期账本消费合计。账单必须**从该卡第一张开始给**（第一张之前按 0），
  否则早期欠款直接漏掉。
- 信用工具 ≠ 证券账户：证券的市值波动账本看不到（必须外部给余额）；信用卡的消费/还款基本都在流水里，
  所以**账本自己在跟踪欠款**，账单的作用是**核对（发现漏记）**而不是提供余额。
- 脱敏的银行侧还款怎么认、负债科目体检怎么分清「期初欠款」与「消费缺失」：
  见 `references/信用卡与负债余额勾稽.md`。

## 用户口径（动配对/动定性前先读）

- **配对关系写死在流水里比靠金额＋日期猜稳**（用户原话：「如果直接写规则太难，可以依靠备注中添加
  UID 来做配对」）。银行流水是 PDF、改不了备注 → UID 只写在**平台侧**（支付宝/微信）的备注列；
  银行侧用「同 UID 平台流水的合计金额、日期最近且唯一」去认。
- **「首先按照时间和金额配对，然后取粒度更细的作为唯一参考标准」**：合并付款（银行侧一笔汇总扣款 ↔
  平台侧多笔订单）保留**平台侧逐笔**（带商品说明/账单类目/本人备注），跳过银行侧那一笔；
  银行账户记账净不变（平台侧各笔的资金科目同样指向这张卡），勾稽照样平。
- **定性只认本人写在账单「备注」列里的标记，不按商户名反推**（用户否决过「按商户建规则」——
  同一家店既可能自己用、也可能送人）。规则用 `memo_any` / `memo_not_any`；没写备注的照常按消费记：
  宁可少记，也不替本人猜。
- **机构原件只读**（`~/Downloads` 的导出件、银行 PDF）：只读处理、中间表另存。用户明确要求给流水
  加标记时，改的是 `Running Account/` 里的**按月件**（解析输入，不是凭据）—— 改前归档到
  `~/Documents/流水归档/修改前原件备份_YYYYMMDD/`，并提醒**重新 `split` 会覆盖这些改动**。
- **用户口述的账户名/定性若与流水原文矛盾 → 摆证据、停下请他核对，不照改**：明细科目名写错
  （把中信银行写成中国银行）账本里没人看得出；脱敏的还款被随口归错，负债就挂在错的明细上。
  证据（平台账单原文 ＋ 卡自家活动名 ＋ 还款摘要）优先于口述；改名/改归属前先让他看一眼卡面或 App。
  同理：他说「找不到这笔」时先确认**是不是他的卡** —— 她的卡不在他手机上，要连「日期 + 金额 +
  交易后余额 + 对账单序号」一起给才能一次找到。

## 三个会静默不生效的接线点

- **列没进记录**：规则按某列判定前，先确认 `parsers/base.py` 的 `REC_COLUMNS` + `record_from_cells`
  真的带上了它。档案里映射了列、装配时被丢掉 → 规则**永远不可能命中，且毫无报错**
  （「备注」列整列被丢过，按备注判定的规则一条都没生效，查了半天才发现备注根本没进记录）。
  补列时同步 `REC_COLUMNS`，中间表也就能直接看到该列，便于人工复核。
- **参数没被入口传**：`book()` 一直收 `adjustments` 参数，而 `cli._prepare` 从不传 → 写了
  `Config/adjustments.yaml` 也不生效。用配置驱动的机制前先 grep 调用链，别只看函数签名。
- **配对关键词表用错**：`_PLATFORM_WITHDRAW` 含「转入」会把平台侧「小荷包-转入」（钱在平台内部走、
  与银行无关）当成提现候选，配走同额同日的银行入账，那笔凭空消失。真提现语义只有
  「提现 / 转出到卡 / 转出到银行卡」。

## 已验证的具体修复（照做）

- **平台侧退款行是「不计收支」（neutral）**：支付宝的「退款-<商品>」、微信的中性交易都是这种方向，
  而退款配对分支若只认 `收支 == "in"` 会**整批漏配**，同一笔退款在平台侧与银行侧各借一次同一张卡。
  判据写 `收支 in ("in", "neutral")` ＋ 摘要含「退款」＋ 结算方式含卡 ＋ 银行侧同额入账。
  这一处修改一次消掉 7 处差（12 处 → 5 处），且不影响其余任何期间。
- **合并付款的组合搜索笔数上限别写小**：实测一次购物车结算可以有 **8 笔**（4.98+23.12+12.04+5.04+
  45.14+41.58+25.80+5.14 = 162.84），上限写 6 会**静默放弃**整组、银行侧与平台侧各记一次。
  候选里还要排除「退款」行，否则同额退款会让组合出现第二个解、解不唯一就整组放弃。
