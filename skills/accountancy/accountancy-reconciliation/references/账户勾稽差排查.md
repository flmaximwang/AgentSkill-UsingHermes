# 账户勾稽差排查（逐处钉到流水）

适用：`book` / `month` 控制台出现 `勾稽[YYYY-MM] <账户>：不一致，差 X`，或账本「配对与问题」表里
有「账户勾稽 … 不一致」。这类差是**金额层面**的（记账净变动 ≠ 流水净变动），与借贷是否平衡无关。

## 0. 先拿回归指标，再动手

```bash
cd /Users/maxim/Documents/Obsidian/wangfanlin4_Accountancy
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts book 2>&1 | grep -cE '不一致'
```

这个数字就是回归指标：**改一处 → 重跑 → 必须变小**。配对是全局的，一处改动会同时牵动所有期间，
所以一次只改一条、每条都跑。

## 1. 诊断：逐处展开到流水级

两套比对都要用，各有盲区：

- **带日期**（`日期 + 金额 + 方向` 的多重集差集）：能看出「哪一天缺了什么」，但**跨日期的同一笔**
  （提现到账、退款延迟入账、平台侧划转）会同时报「缺」和「多」，净额却是平的 —— 拿它当差的成因
  会把人带偏（盯着一笔「缺」的 200.00 查了很久，那处其实本来就平）。
- **纯金额**（只按 `金额 + 方向` 做多重集）：跨日期不干扰，直接给出「记账多/记账少」的金额清单。

差的成分 = 多 − 少。拿「多/少」的具体金额**回流水里找那几笔**（同金额、该账户、日期邻近），
再逐笔看它是**哪条规则命中、有没有被跳过、跳过原因写的是什么**。

数据来源：`res["entries"]` 是**凭证级**的（一行一张，含 `借方合计`/`贷方合计`），要看**分录明细**
得读 `e["行"]`（含 `明细` / `借方金额` / `贷方金额`），或直接读账本「记账凭证」表的 `明细科目` 列。

## 2. 定位「谁把它跳过了」

按配对链顺序逐个调用配对函数，打印目标流水在**哪一步**被跳过、`_pair_skip` 原文 —— 比读代码猜快得多：

```python
kept, jd = pair_jd_duplicates(records)
kept, t  = pair_internal_transfers(kept, cfg)
kept, c  = pair_card_funded(kept, cfg)
kept, o  = pair_own_account_transfers(kept, cfg)
# 汇总 skipped，按 (源文件, 源行号) 建索引，再查目标流水落在哪一步
```

账本「配对与问题」表里有同样的原因文本（`_pair_skip` / `_no_entry` 原文），可按金额直接 grep。

## 3. 已确证的根因（按出现频率）

1. **平台侧退款行是 neutral**：配对分支只认 `收支 == "in"` → 整批漏配，退款在平台侧与银行侧各借一次卡。
2. **配对关键词含「转入」**：平台侧「小荷包-转入」（与银行无关）被当成提现候选，把同额同日的银行
   入账配走 → 那笔凭空消失。
3. **合并付款笔数上限写小**：一拖多搜索的 `max_items` 写死 6 时，8 笔的组合被**静默放弃**，
   银行侧与平台侧各记一次。
4. **配对断链（两头都没入账）**：几条配对规则各跑一遍、互相看不见对方跳过了什么，会出现
   「银行侧 B 因『平台侧 P 会入账』被跳过，而 P 又因『另一笔流水会入账』被跳过」—— 钱凭空消失。
   判定要看**对手是不是真的入账了**，而不是「存在某个同额记录」。
5. **一笔流水被两套配对规则争用**：同一笔银行转出既被「卡结算并进银行」认领成平台充值、又被
   「自有账户划转」当成转出侧；它按前者的科目入账，后者却假设它会记成「借对方卡 / 贷本卡」，
   于是把对方的转入行跳过 → 对方账户少一笔。
   **修的方向是让配对互斥（一笔流水只被一套规则采用）＋收紧跨日窗口（提现/转账这类要求同日，
   只有退款允许放宽）—— 这两条尚未实测验证，动手前先照第 0 节的回归指标试。**

## 4. 修复纪律

- **只收紧，不放宽**：宽判据实测代价 —— 一次运行多认 1,770 笔（凭证 3,484 → 5,254），
  差从 12 处炸到 32 处。
- **先预测再跑**：算出「改完这处差应该变成多少」，跑完对不上就说明还牵动了别处；
  对得上才敢确认这处修改的边界。
- **回归了先回退再分析**。
- 修完必看：① 不一致处数下降 ② 每期 `check` 仍「通过」③ 待分类仍为 0
  ④ 变化的「配对跳过」条数都能解释。

## 5. 显式配对：备注里的 UID

- 标记写在**平台侧**备注列（形如 `配对UID:K20260111A`）—— 银行流水是 PDF、改不了备注，
  所以只能单侧标注：用「同 UID 平台流水的合计金额」去银行侧找那一笔。
- 同一 UID 的多笔平台流水 = 同一次结算，合计 = 银行侧那一笔（平台侧保留、银行侧跳过）。
- 匹配顺序照用户口径：**先按时间和金额筛，再取日期最接近的一档；这一档仍不唯一就不动**
  （错配比不配更糟）。不唯一要打印诊断（候选几笔、日期最近几笔、合计多少），别静默跳过。
- 保留侧要**隔离出配对链之外**再并入，否则后面的规则会按「该笔由银行卡结算」把它再跳一次，白配。
  ⚠️ 隔离前先确认那一笔的**规则方向是对的**：实测「小荷包-转出到银行卡」这类行被隔离后按错误方向
  入账（记成从卡扣款），差反而变大 —— 那种根因在规则、不在配对，UID 解决不了，该撤回标注别硬留。

## 6. 机制存在 ≠ 生效

配置驱动的机制要确认**入口真的加载了它**：`book()` 一直收 `adjustments` 参数，而 `cli._prepare`
从不传 → 写了 `Config/adjustments.yaml` 也不会生效。用之前先看调用链（grep 参数名）。
