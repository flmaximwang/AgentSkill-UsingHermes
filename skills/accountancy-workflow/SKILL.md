# 流水 → 记账凭证（主流程）

环境（两条口径，别混）：

- **用户自己终端**：先 `conda activate Accountancy`（micromamba，环境已登记；`which python` 必须是
  `/Applications/Accountancy/bin/python`），再 `cd` 项目根敲 `python -m Scripts ...`。
- **Agent / 脚本 / cron（不激活）**：用绝对解释器 + 去 PYTHONPATH：
  `env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts ...`，cwd 必须是项目根
  （不带 cd 会报 `No module named Scripts`）。

> **不加前缀的 `python` 是个陷阱**：Hermes 的 shell 里它是 hermes venv 的 python，用户登录 shell 里是
> `/Users/maxim/.local/bin/python`（homebrew 3.11，**没装 yaml/openpyxl**）——都会以
> `ModuleNotFoundError` 失败。而 `python -m Scripts --version` 这类只用标准库的命令仍然“成功”，
> 很容易误判成环境没问题。验证环境用 `python -c "import yaml, openpyxl"`，不要用 `--version`。
> 曾经为了免激活做了个 `记账.sh` 包装，用户明确不要（“多一个入口”）：**别再建 shell 包装/别名**，
> 统一用上面的模块命令。

## 首选入口：一条命令算某个月（用户问"这月的账"时就跑它）

```bash
cd /Users/maxim/Documents/Obsidian/wangfanlin4_Accountancy
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts month 202608
# 用户自己终端里就是：conda activate Accountancy 之后 python -m Scripts month 202608
```

期间是唯一可变参数：`202608` / `2026-08` / `2026/8` / `2026年8月` 都接受（归一成 `2026-08`）。

它一次做完 normalize + book（只出该期）+ 独立复核（与 `check` 同一实现 `export.verify_workbook`）+
打印交付报告，报告的 ①②③④ 正好是交付汇报要的四段：① 归集对账（每份导出文件的笔数/收支合计，
锚点=文件自带统计）② 凭证张数与借贷合计 ③ 待分类清单（笔数/金额/原因）④ 需确认事项。

- 退出码：`0` 通过可交付 ｜ `1` 校验不通过（不许录入）｜ `2` 期间非法 / 该期无流水 / 读不到流水。
- `month` / `book --period` 的 ① 归集对账**只列本期相关文件**（含本期流水的，或文件名区间覆盖本期的
  空月文件），其余压成一行汇总（“另有 N 份…”）。输入仍然读整个 `Running Account/`（跨月银行文件会同时
  贡献相邻两期），只是**显示**按期间过滤 —— 否则期间一攒多了，翻一个月的账要刷几十行没用的文件。
  全部文件清单看 `normalize`（它本来就是全量盘点）。
- 期间**不合法或该期没有流水就报错退出并列出「现有期间」，绝不猜一个月份**（猜错等于把账记到别的期间）。
- `month` 只决定**出哪一期的账本**，输入仍读整个 `Running Account/`：跨月银行流水按日期分组，
  按文件名筛月会丢月初/月末的几笔，所以不要"顺手"按文件名过滤输入。
- 只是想把所有期间的账本刷一遍、或做单期调试 → 用 `book`（可加 `--period`）；
  要给人汇报就用 `month`（`book --period` 不做独立复核、也不出汇总报告）。

## 信用卡账单（负债侧，2026-09 接入）

信用卡的**未还余额只能从账单读**（平台/银行流水里读不出来）。已接入的账单来源：
`skills/boc-credit-statement`（中国银行信用卡-9393，PDF）与 `Asset Balance/信用卡账单.tsv`（中信-0270）。

- **还款行的资金来源不写在账单里**（只有 `BOCNET` / `支付宝CHN` / `还款成功 , 谢谢 !` 这类描述）
  → 资金来源**只认资金侧**（借记卡/支付宝/微信流水里那笔转出），按「日期 + 金额」配对，
  配上就**跳过账单侧**（否则同一笔钱入账两遍）；配不上的 = 钱来自**没有流水的账户**
  → 挂账或让用户补流水，别猜。
- 账单侧与平台侧出现同一笔消费时，**保留账单侧**（它是卡的完整台账，含分期/冲销/利息），
  把平台侧的商品说明/类目**回填**进账单行的摘要（同 `pair_jd_duplicates` 的做法）。
- 账单自带「上期余额 / 本期支出 / 本期存入 / 本期余额」四数，是**逐份对账锚点**，
  解析后必须核对（见 `parsers/boc_credit.check_records`）。
- **分期**：`自由分期成功，冲销原交易金额`（存入列）冲减原消费，同期的 `<00x/00y>…分期`（支出列）
  是重记的本金 → 两行必须成对处理，否则费用重复或漏记；`分期利息` 才是真成本。

## 资产表：`balances`（每期期末＝下期期初的实际资产量）

账本「统计」表只有**本期变动**，没有期初/期末余额。银行流水自带余额列，但**平台/投资账户的账单里没有**
（证券账户最明显：1101 只记银证转账，持仓市值与浮盈亏在流水里根本不存在）。所以「期末实际有多少钱」
只能由外部（券商 App / 银行 App / 平台余额页）提供。

**数据文件是 `Asset Balance/资产表.tsv`（人工维护的 **TSV**，不是本工具的产物）**——用制表符分隔：
口径/备注里常有半角逗号（`1,860.79`），CSV 下会被 Excel 拆列——用户明确要求：
资产表是一个 csv、放在 `Asset Balance/` 而不是 Config/。一行 = 一个账户在一个期间的期末余额
（同时就是下期的期初），**不按期间分文件**（逐期累加、改名/拆月会丢掉「上期余额」这条链）。
口径与列说明写在文件开头的 `#` 说明行里（与数据在一起），加载器跳过 `#` 行与空行。

```bash
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts balances            # 资产表 + 勾稽 + 余额链自检
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts balances --period 2026-08
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts balances --check      # 银行差额必须 0，否则退出码 1
```

列（`期间,期末日期,账户,科目编码,金额,口径,来源,备注`，表头缺列即报错）：

- **账户填 account_map 的明细科目名**（人可读，如 `证券资金账户`），也接受账户键；
  **科目编码必须与 account_map 一致**（写错即报错 —— 防把负债记成资产）；性质（资产/负债）由编码推出，
  不单独设列（少一列就少一处能自相矛盾的地方）。
- `期末日期` 按**数字**比（Excel 另存会把 2026-08-31 变成 2026/8/31）；`口径`/`来源` 必填；
  同一账户同一期不得重复；金额非负。
- **口径没定的写「…｜待确认」**，`balances` 会在末尾单独点名（数字先录、口径后补，但绝不假装已确认）。
- 文件用 `utf-8-sig` 读写（Excel 双击不乱码）；字段含半角逗号要加引号。

- **银行账户不用人工录**：取流水「余额」列 ≤ 期末 23:59:59 的**最后一笔**（本期无发生额就结转上一期）；
  证券账户的账户键是 `securities`，明细科目名 **国信证券-3163**（1101 短期投资；用户 2026-09-23 点名，
  之前叫「证券资金账户」）—— 改明细科目名后**必须重出全部账本**（`book`），否则资产表按明细名 join 不上。
  **期初**也能推：`首笔余额 − 该笔金额`（如 2026-01 中行 3358 = 2,080.92），只在最早有记录那一期用。
  **必须按完整时间戳排序** —— 中行同一天的明细在 PDF 里是倒序，只按日期排会取到当天最早那笔的余额
  （实测伪造出 11 个假差额，其中一个 4,450.00）。
- **勾稽**：`上期余额 + 本期净变动（只读账本「统计」表，不重算分录） = 本期余额`，差额单列。
  差额 = 从流水**读不出来**的部分（市值波动 / 账户内交易费用 / 分红利息），**是信息不是错账**；
  银行账户的差额必须为 0（非 0 且等于本期待分类银行净额 → 不算错账；否则必须查）。
  没有上期余额的首期标「首期锚点」，**不假装勾稽得平**（例：证券账户 2026-08 的 54,542.00 ——
  2026-01-01 期初未知，但 2026-01-05 转出 34,000 可证期初不为 0）。
- **差额不自动进账本，但「市值口径账户」可以按月调**（用户 2026-09-23 确认）：
  只在 `account_map.yaml` 的 `fair_value_accounts` 里登记过的账户（现：`securities` → `securities_fair`
  = 5111 投资收益—证券市值调整）才会自动生成调整分录；没登记的（银行/平台）差额只备查。
  ```bash
  env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts balances --adjustments --dry-run
  env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts balances --adjustments   # 写 Config/adjustments.yaml（按期间幂等）
  env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts book                    # 重出账本 → 差额归零
  ```
  浮盈：借 1101 资金账户 / 贷 5111；浮亏反向。id = `调-<期间>-市值-<账户键>`，`依据` 写清算式（可逐条复核）。
  调完必须验：①`balances --check` 差额 0.00 ②逐期 `check` 借贷平 ③恒等式勾稽与现金勾稽仍为 0
  （调整不动货币资金，所以现金勾稽不受影响；资产/损益同增同减，恒等式仍平）。
  ⚠ 这是**个人口径的市值法**，不是小企业准则的成本法（准则下短期投资按成本计量、持有期间不确认
  公允价值变动）—— 口径写在 `fair_value_accounts` 上方，改口径改那里再重跑两条命令。
  **按月调后处置不会重复计收益**：1101 的余额已 = 市值，卖出减少的市值正好等于收到的现金。
- **余额链自检**（`balances` 顺带跑）：银行流水逐笔 `余额_i − 余额_{i−1} == ±金额_i`。
  它比文件自带的笔数/收支合计锚点更强（锚点对得上仍可能「少解析一笔 + 多解析一笔」或方向记反）。
  2026-01~08 四卡 2037 笔断点 0；**同一秒内多笔**先后不可知，组内互换不算断点。
- 银行账户也可以人工录：那就与流水余额逐分比对，不一致报错（先核对数字来源，别改账本）。

### 信用卡：没有月末余额可读 → 账单台账 + 账本推导

账单**不在月末出**（各卡自己一天，如中信 0270 是每月 16 日），用户只能给「每期账单金额」→ 别让他
去 App 读「未还余额」。数据文件 `Asset Balance/信用卡账单.tsv`（人工维护，同为 TSV：账户/账单日/账单金额/
到期还款日/来源/备注；账户必须是**负债**科目；**从该卡第一张账单开始给**，第一张之前按 0）。

- **账单口径欠款** = Σ账单（账单日 ≤ 期末） − Σ账本借方（还款/退款，≤ 期末）
- **账本口径欠款** = Σ账本贷方（消费） − Σ账本借方（还款/退款，≤ 期末），期初 0
- 两者的差 = 账单日之后到期末的**未出账消费** + 账单未覆盖的消费（线下刷卡等没进流水的）

资产表里信用卡按**账本口径**列示（含未出账消费 = 真实欠款），来源标「账本推导（账单台账仅作核对）」；
账单只当核对锚点。**账单口径会系统性少算未出账那一段**，别拿它当余额。
校验靠两个事实：①还款额应当 = 上一张账单（0270：7/3 还 1,860.79、8/4 还 2,057.43，一分不差）
②第一张账单金额 ≈ 该周期账本消费合计（差几十元 = 卡的记账日期与平台交易日差 1–2 天、跨了周期边界）。

### 信用卡/信用工具的负债科目：负数 = 只有还款没消费

`balances`/账本里看到 2241/2001 某明细累计净变动是负数（借方余额），先分清两种情况：
① **期初欠款**（2026-01 之前欠的，在 2026 年被还掉）——正常，如美团借钱 −30,385.07（1/5 还 3.5 万）；
② **消费根本不在我们的四个来源里** —— 如**美团月付**（美团自己的信用支付，账单只在美团 App，
   四个来源里 0 条「月付」结算方式）→ 只有还款没有消费，只能挂负数或把还款当费用。
用 `统计` 表的逐明细「本期增加/减少」一次体检全部负债科目就能分出来（增加=0 就是 ②）。
银行脱敏的「***还款」/「***月付」：建行只留户名最后两字，两者都是**美团月付还款**
（用户 2026-09-23 确认，规则 `bank-credit-repay-masked` → meituan_pay）。

## 跨期趋势图：`trend`（读账本「统计」表画图）

三个面板：利润（净利润）、资产（Δ现金、Δ短期投资）、负债（Δ负债）；**柱＝当月净变动，线＝自首期起累计净变动**。

### 交互式（默认）vs 静态（`--formats png,svg,pdf`）

- 用户明确要**交互式是为了「直接读数」**，不是好看：所以必须 `hovermode="x unified"` ——
  鼠标停一下就把该月**全部序列**的精确值列出来（实测「04月｜净利润（当月）: 8,525.46 元｜累计净利润: 18,406.66 元」）。
  只给单点 hover 还得到处找，等于没解决他的问题。
- **两块渲染共用一个取数函数 `series_values()`**：柱/线的取值、缺口月给 None 的逻辑只写一处 ——
  两套取数迟早分岔（而分岔的图比没有图更糟）。只管渲染色调不同。
- **默认内嵌 plotly.js**（`include_plotlyjs=True`，文件约 4.6 MB）：账务报表要能离线打开、可归档，
  不把“打开时需要联网”当默认；文件小用 `--plotly-cdn`（几十 KB）换，由用户选。
- 版面最小化照旧：无总标题、无页脚、无图下数字表；逐月数字仍打终端。

### plotly 的坑（都踩过）

- **`shared_xaxes=True` 会把非最下面板的 x 刻度标签隐掉**：面板很高时中间那块读数要找上下参照，
  必须在循环后再 `fig.update_xaxes(showticklabels=True)` 强制全显（三轴仍共享区间，缩放依旧同步）。
- **`subplot_titles` 默认居中**，与静态图的左对齐不一致：
  `for ann in fig.layout.annotations: ann.update(x=0, xanchor="left")`。
- **图例不合并成一个**：三块面板的序列名不同，合并后读不出对应关系 —— 用 `legend / legend2 / legend3`
  分组，位置用 `fig.layout.yaxisN.domain[1]` 贴到各自面板上沿右对齐（写死 y 会在行数/间距改动时错位）。
- **缺口月**：柱不传该点、累计线用 `None`（配 `connectgaps=False`）才断开，横轴标签写「（无账本）」——
  与静态图同一口径，两条路各写一套就会一边断一边连。
- 依赖：`env -u PYTHONPATH /Applications/Accountancy/bin/python -m pip install plotly`
  （纯 wheel + 自带 js，不动 numpy/pandas）。延迟导入，报错里给安装命令。
- **验证方式**：拿浏览器打开 `file://` 的 HTML，用 CDP 派 `Input.dispatchMouseEvent` 真的悬停一下
  再看 `.hoverlayer text` 的内容 —— 比对终端数字表，别只看“渲染出来了没”。截图另附。

### 共同的纪律（两种渲染都要守）

- **只读账本、不重算分录**：数据取自 `Account Book/` 各期「统计」表的**本期净变动**列（已过 `check` 复核）。
  另起一套算法重算就是第二套口径，迟早与账本对不上，而且没人看得出哪个对。
- **只画变动，不画余额**：期初余额无法从流水取得（平台账单没有余额列），给"推算的期初"会让图上
  出现看着精确、实际不可核验的余额。累计列的口径 = 自首期起逐月净变动累加，措辞必须写「累计…变动」。
- **先复核再出图**：每期必须 ①`check` 通过 ②资产−负债−权益=0 ③现金净增加额−货币资金净变动=0
  ④净利润==权益合计 ⑤资产合计==现金+短投+其他应收款+固定资产净值。任一条不成立 → 打印全部问题、退出、**不写任何图**。
- **缺口默认报错**（缺月的走势图会骗人），`--allow-gaps` 才画，且缺口月横轴标「（无账本）」、柱不画、
  累计线断开（matplotlib 传 `None` 即自动断线），绝不当作 0。
- **待分类不在「统计」表里**（未生成凭证）→ 图上数字不含它们，必须逐期打在终端（银行侧/平台侧分开报）。

### matplotlib 的坑（只影响静态图）

- **图要最小**：用户明确不要总标题、页脚注释、图下数字表 —— 只留三块趋势＋图例＋坐标轴＋月份。
  逐月数字打在终端（`render_terminal`）。别再"好心"加回说明文字。
- **依赖 matplotlib**（环境里原本没有）：装法是
  `env -u PYTHONPATH /Applications/Accountancy/bin/python -m pip install matplotlib`（纯 wheel，不动 numpy/pandas）。
  代码里延迟导入并在报错里给出这条命令，不要用自绘 SVG 兜底 —— 那是两套渲染要维护。

## Step 0 入库：多期导出文件先按月拆分

导出的起止区间是任意的（可能一次导 2026-01-01~2026-07-31），而本项目一个月一本账。
**跨期文件先用 `split` 拆成按月文件再入库**，别指望 `book` 按日期分组去"消化"它——账本能分组，
但对账锚点对不上（文件自带的「共N笔/收入/支出」是全期的）。

```bash
cd /Users/maxim/Documents/Obsidian/wangfanlin4_Accountancy
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts split "<文件>..." [--dry-run] [--force] [--account 3358]
# 产物：Running Account/<out_dir>/<out_stem>_<导出账号>_YYYYMMDD_YYYYMMDD.<ext>（月份区间 = 该月首日/末日）
```

- 命名约定 = `<来源>[_<导出账号>]_YYYYMMDD_YYYYMMDD.<ext>`，**定义在 `Scripts/paths.py`**
  （`running_file_name` / `split_running_name`）—— 读与写都走它，别在脚本里手拼文件名。
- **`<导出账号>` 段是账户（钱在哪张卡）的唯一依据**：卡尾号 `3358`/`2464`、支付宝/微信/京东账号尾号 `7226`，
  它对应档案里该账户的 `accounts` 键。`split` 的判定顺序是「文件名账号段 → 抬头完整卡号/账号/昵称 →
  档案里唯一的账号」，**认不出就报错**（用 `--account 3358` 人工点名），绝不按来源猜账户；
  文件名说的账号与抬头内容矛盾（`_3358_` 的文件里写着 2464 的卡号）也报错停下。
- 目标目录取自账号/档案的 `out_dir`（建行：档案名 建设银行，但目录与文件都叫 中国建设银行），
  没配才退回从源文件名推。
- 说明块原样保留，但统计行按**本月明细逐笔累加**重算，并加一行「拆分说明」记出处 —— 拆分件不是
  银行/平台原始回单，别当凭据用。
- **空月也要出文件**：出文件的期间 = 实际有流水的月 ∪ 文件声明的起止区间（如建行那份声明 20260101-20260731
  但 7 月无发生额 → 也要出一份 0 行的 2026-07）。缺月比空文件难发现；区间读不到就只按有流水的月出。
- **银行 PDF 不能整页复制**（月份边界落在页中间：中行 31 页里 6 页跨月，建行整份 1 页跨 6 个月——
  整页放进两个文件 = 同一笔重复入账）。`split` 对 PDF 的做法是**按抽出的明细重排生成「派生件」PDF**：
  保留原列名与原取值、页首写「派生件（非银行原始回单）+ 源文件名 + 原件卡号/客户/期间」，
  且**写入前回读自检**（写临时文件 → 用解析器读回 → 逐笔比对源明细，不一致就不写）。
  抬头里的「页数 1/31」「借方发生数 552.80」等**只对原件成立**的数字绝不搬进派生件（会被当成该月锚点）。
- **多期原件必须留在 `Running Account/` 之外**（如 `~/Downloads`）：全期文件与按月文件同时存在会被
  `normalize` 各解析一遍 → 同一笔钱重复入账。`split` 对位于该目录内的源文件直接拒绝（别用 `--force` 绕过）。
- 已存在的按月文件默认不覆盖（避免把已入账期间悄悄换成新口径），要覆盖得显式 `--force`。
- 拆完**必须复核**（踩过三次：xlsx 数据行照抄原行号造出空白文件；页首支出/收入写反；漏出空月）：
  ① 每个按月文件的「总行数 = 说明块行数 + 本月笔数」（xlsx）/「行数 = 本月笔数」（PDF）；
  ② 用 `parse.normalize` 逐文件解析，各月笔数与收/支/中性合计 = 源文件逐笔累加的分月结果；
  ③ 各月「日期/金额/收支/交易单号/摘要/对方」多重集拼起来 == 源文件，缺 0 多 0；
  ④ PDF 派生件还要核对页首声明的笔数/支出/收入 == 该页明细累加（不能只看行内容，那个数字曾写反）。

## 解析器按来源分模块（`Scripts/parsers/`）

```
parsers/__init__.py   引擎：档案 → 来源解析器 → 统一中间表（含重复文件护栏、账户判定）
parsers/base.py       与来源无关的零件：表头定位 / 金额 / 日期 / 账号判定 / 记录装配 / 对账
parsers/bank.py       银行 PDF（中行借记卡 / 建行储蓄卡）：pdf_table 按坐标抽表 + 折行归属
parsers/alipay.py     支付宝交易明细 CSV（GB18030、表头行不固定）
parsers/wechat.py     微信支付账单 XLSX（前 16 行说明、日期是序列号、中性交易）
parsers/jd.py         京东/京东金融 CSV（金额带退款括注、订单号会重复）
parsers/manual.py     人工补录 CSV（手写文件：列数护栏 + 单号前缀/唯一性）
```

- 每个来源模块三件事：`read_cells(path, profile)`（文件 → 行 dict）、`check_profile(profile)`
  （档案自检，缺关键字段立刻报错，别等解析出来是错的才知道）、可选的 `amount_of` / `check_records`。
  **加一个新来源 = 档案加一段 + 写一个模块 + 在 `parsers.PARSERS` 注册 + 写 skill**。
- `Scripts/parse.py` 现在只是**转发层**（老调用 `from . import parse` 继续可用）：
  新代码直接 `from . import parsers`，别在 parse.py 里加东西。
- `parsers.normalize_dir()` 返回 **4 元组** `(记录, 错误, 逐文件统计, 重复文件清单)` —— 第 4 项要打印进
  ① 归集对账、并写进账本「配对与问题」表（否则「条数怎么少了一半」没人看得出来）。
- **同一份导出出现两份（改了名/复制了一份）按 sha256 只归集一份**：每组保留「带已登记导出账号段」
  的那一份（`中国银行_3358_…` 优先于 `中国银行_…`），其余写进「重复文件」行。用户按导出账号改名后
  老文件常还留在原地 —— 不去重就是整月流水入账两遍（实测 34 份副本：4216 条 vs 正确的 2154 条）。

## Step 2 映射：先看命中分布，再决定是否改规则

**分析 ≠ 规则（重要纪律）**：对话里给出的分类归纳（如"这些商户属于餐饮"）只是一次性统计，
**不会影响记账**。只有写进 `config/account_map.yaml` 的规则才生效。所以：
- 明确可判的商户（品牌名能定性）→ **当场写规则**，别丢进待分类；
- 只有归属性真的不明（某人转账、平台自营专户、脱敏商户）才留待分类。
- 消费类规则用 `directions: [out, neutral]`：平台把用余额/小荷包/信用支付的花费记为
  「不计收支」，那也是真实花费，只写 `direction: out` 会整批漏掉。

```bash
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts book
# 账本按月归类：Account Book/记账凭证表_YYYYMMDD_YYYYMMDD.xlsx（不建月份文件夹）；只出某期加 --period 2026-08
```
规则在 `Config/account_map.yaml`（改数据不改代码），账户档案在 `Config/bank_profiles.yaml`。
**未命中的流水不会生成凭证**，只进「待分类」表 —— 这是刻意的：宁缺勿猜。

## Step 3 分录生成（自动）

借贷方向铁律：资金流入 → 借记资金科目；资金流出 → 贷记资金科目。
- 收入进账：借 银行存款/其他货币资金；贷 收入（不含税）+ 贷 应交税费—应交增值税（销项税额）
- 费用支出：借 费用（不含税）[+ 借 进项税额]；贷 资金
- 提现/内部划转：借 到账账户 + 借 财务费用—手续费；贷 出账账户（到账额 + 手续费）
  规则里 `to` = 资金流入方（借方）、`from` = 资金流出方（贷方），**没有隐式方向对调**；
  收入方向的划转（银行「银联入账」、证券转回银行）必须另写一条 `direction: in` 的规则，
  否则会出现 借=贷 反向的凭证。
- 退款：借 资金；贷 原成本费用（冲回）

## Step 4 硬校验（不通过就不许录入）

- 每张凭证 Σ借方 == Σ贷方，差额非 0 直接报错，**绝不允许「硬凑平」**；
- 科目编码必须存在于 `config/chart_of_accounts.yaml`（小企业会计准则 66 个科目），否则报错；
- 同一交易单号重复出现 → 记入问题清单并跳过。

## Step 5 交付与复核

**账户勾稽的差额要先扣掉本期待分类金额**：待分类流水不生成凭证，银行账户的「流水净变动」里天然
包含它们，不减就会每期都报假的「不一致，差 XXX —— 必须查」（2026-07 报的 686.58 全是 2 笔待分类：
666.66 + 19.92）。扣掉后残差必须为 0；报假警报比不报更糟——以后真丢账就没人信了。

产物：`Account Book/记账凭证表_YYYYMMDD_YYYYMMDD.xlsx`（**按月归类，一个月一本**；**不建月份文件夹**，
期间写在文件名里 —— 与 `Running Account/` 的导出文件同一写法，文件名区间 = 该月首日/末日）
**表内只有数据、没有任何合计行**，
五个工作表：
记账凭证（一行一条分录，凭证号每行都写）｜统计｜待分类｜配对与问题｜规则命中。

**账本目录就一个平铺目录**（不再有 `Account Book/YYYY-MM/` 子目录）：文件名即期间，`ls` 一眼看全所有月份。

```bash
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts check \
  --workbook "Account Book/记账凭证表_20260801_20260831.xlsx"
```
合计与试算平衡由 **code 负责**：`book`/`month` 对每期跑内存校验 + 读回 xlsx 复核，结果只打印到控制台。
**不再写 `记账凭证表_校验.json` 旁挂文件**（用户明确不要 —— 交付物就是 xlsx 一本）。交付前每期都要是
`通过`；`check` 命令可随时独立重跑复核。

## 固定资产与折旧：台账 → 人工补录 → 分录（2026-09 起）

**电子设备是资产不是当期费用**（用户口径：单件原值 ≥ 500 元资本化；直线法 12 个月；残值 0%；
**购入次月**起计提；尾差落最后一期）。三件事分开放，别混：

| 环节 | 数据来源 | 分录 |
|---|---|---|
| 取得 | 规则（`asset_buy`）命中设备那笔真实流水 | 借 1601／贷 资金或信用工具（走 `$settlement`，信用卡付的挂 2241） |
| 折旧计算 | **只认 `Config/fixed_assets.yaml` 台账** | 借 5602 生活支出-折旧／贷 1602 累计折旧（**不动货币资金**） |
| 折旧进流水 | `assets --write` 生成 `人工补录` 行的「折旧计提-<资产ID>」 | 再由规则 `depreciate` 入账 |

```bash
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts assets            # 查表 + 逐期折旧计划
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts assets --write    # 写折旧行（默认写到最新账本期间）
env -u PYTHONPATH /Applications/Accountancy/bin/python -m Scripts assets --check    # 三方勾稽，不符即退出码 1
```

- **折旧额绝不手写进流水**：一律由台账算（手写的数字没人能复核）；台账是折旧的唯一数据源。
- **折旧走「人工补录」不是偷懒**：折旧在任何银行/平台账单里都不存在，只有人工补录这条通道能把它送进
  流水层。业务类型必须**一条设备一个**（`折旧计提-FA-2026-001`），否则一条规则管不了不同设备的
  1602 明细 —— 我们要在账本里**逐件**看到已提折旧。
- 两个新 `entry_type`（`rules.ENTRY_TYPE_PARAMS` + `books.build_lines` + `ENTRY_TYPE_LABEL` 三处都要加）：
  `asset_buy`（借资产/贷资金）、`depreciate`（借费用/贷 1602，**全项目唯一没有资金腿的形状**）。
- **1602 是备抵科目**：归在「资产」块但增加在**贷方**。`stats.py` 里方向必须按科目码判
  （`debit_natured(code, block)`，`CONTRA_ASSET_CODES`），资产合计要写成
  `货币资金 + 短投 + 其他应收款 + 1601 − 1602`；`trend.py` 的「⑤资产合计=现金+投资+应收+固定资产净值」
  同步改。忘了改 → 恒等式残差报警，或「越提折旧资产越大」这种静默的方向错。
- **购建固定资产的支出归投资活动**（`stats.CAPEX_CODES` 并入 `INVEST_CODES` 判断），
  不是经营活动：资本化后那笔现金流出会从「经营活动净额」挪到「投资活动净额」（现金净增加额不变）。
- 台账「出处」必须能回溯（`源文件:源行号`）—— `assets --check` 会逐笔回流水中间表核对金额；
  账本里 1601 借方发生额必须逐个设备等于台账原值，1602 贷方必须等于台账逐期折旧。
- 关键词锚在**型号串**上（「耀世16ultra」「MX Master4」），不要用厂商名：同一订单在账单里还有
  「交易关闭」的中性兄弟行（2026-04-19 两条 9,900.00），厂商名会误命中。
- 退货/退款**不写自动规则**：按已提折旧拆（冲 1601 原值、冲 1602 已提、差额进当期损益），人工处理。

## 重复入账防护（四个真实陷阱）

同一笔钱常出现在两个文件里，重复入账会虚增资金与收入。`books.pair_*` 已处理：
1. 平台提现 → 银行入账：保留平台侧（手续费可见），银行侧跳过；
2. 平台支出由银行卡结算（结算方式写着某银行卡）→ 保留银行侧，平台侧跳过并把商品说明回填摘要；
3. 平台「转出到银行卡」与银行「银联入账」都是收入 → 保留银行侧，避免收入算两遍；
4. **京东（`pair_jd_duplicates`）**：京东回单是订单/支付视角，同一笔钱常同时出现在微信/支付宝**和**银行——
   「白条分分卡-微信/支付宝(南京银行)」↔ 账单里的「南京银行储蓄卡(0134)」（南京银行是分分卡的卡面银行）；
   「中国银行储蓄卡(3358)/建设银行储蓄卡(2464)」↔ 银行「网上快捷支付/消费」。一律只留既有账户侧，
   京东方跳过；配到银行侧时还要把京东的商品说明**回填**进银行侧摘要（银行摘要只有「网上快捷支付｜网银在线」这种壳子）。
   **它必须最先跑**（`book()` 里排在 `pair_internal_transfers/pair_card_funded` 之前）：晚跑时被卡结算的账单行
   已从池子里拿掉，京东侧就配不上而落进待分类。
   金额对不上但确属同笔的（京东「白条主动还款 684.90」↔ 银行扣 684.40），只在「资金动作 + 银行流水带京东
   字样 + 差额 ≤1 元」时照配，差额写进跳过原因并报人工确认 —— 绝不静默吞掉。
5. **同一份导出存在两份（改名/复制）**：按内容 sha256 去重，每组只解析一份，跳过原因写进「配对与问题」
   表的「重复文件」行（含 sha256 前 12 位）。用户按导出账号给文件改名时，老名字的文件常还留在原地 ——
   不去重就是整月流水入账两遍。内容相同却指向**不同**导出账号（`_3358_` 与 `_2464_` 两份一模一样）
   → 报错停下，先核对文件。

跳过的每一笔都会写进「校验」表并给出原因，可逐条复核。

## 配对去重的三条硬约束（2026-09 修，血泪）

1. **只有「钱确实从某张已导出的借记卡走」才允许配对**（`books._funding_is_tracked`）：结算方式里的
   出资渠道要解析到**已导出的 1002 账户**（本次运行里出现在银行流水中的 `_money_account`）。
   花呗/白条分分卡/信用卡付的消费，以及工行 8935 等**未导出流水**的卡扣的钱，银行对账单里
   根本没有这一笔；按同额去银行流水里捞，只会把平台侧那笔**并进一条不相干的银行流水**，
   平台侧再也入不了账。实测：2026-01-11 微信云裳物联 2.00（分分卡）并进了 01-07 中行一笔 2.00；
   2026-01-29 医疗费 10.00（中行信用卡 9393）并进了 02-02 中行借记卡的 10.00；
   2026-07 五天的「小荷包-自动攒 10.00」（工行卡）全并进了 07-30 那一条。
2. **一条银行流水只认领一条平台流水**（`_nearest(..., used=)` + `used_in/used_out/used_platform`），
   同日并列时再按**时分秒**就近。否则同额的多条平台流水全并进同一条银行流水（2026-01-30 三笔
   蚂蚁财富买入 100 全并进 11:03:27 那条），拿到说明的银行流水只剩一条，另外两条**光秃秃地落进
   待分类**（摘要只有「网上快捷支付｜支付宝｜银企对接」，看不出是什么），而没被配走的平台流水被静默跳过。
   建行等只有日期的流水保持「先到先得」，不能凭空造时间。
3. **认领要按「谁离得近」而不是「谁先出现」**：拿到说明的应该是时间上对应的那一条。

修完必须做的验证：① 银行逐账户勾稽仍为「一致」（银行侧没被动过）；② 蚂蚁财富这类
「银行侧买入 ↔ 支付宝侧买入」的**两侧金额合计必须逐分相等**（本次 39 笔 3,403.50 ↔ 3,403.50）；
③ 逐期把「配对与问题」扫一遍（跳过条数会变，属正常）。

## 待分类清零的两条通用手法

- **按账单自带的「交易分类/交易类型」归类**（支付宝 `交易分类`、微信 `交易类型`）：写成

  恰好出现同样字样时误命中。优先级放在具体商户规则**之下**（73），只在按商户名判不出时才用。
  新增这一档明细时要同步 README 的明细表。
- **删掉过宽的商户关键词**：`grocery` 里的「收纳」「家居」把收纳袋/置物架/显示器增高架整批
  拐进「食品日用」，退款回冲时科目就对不上（原单在食品日用、退款按类目冲数码）。

## 「不生成凭证」与「待分类」是两回事（`no_entry`）

已定性、但**没有任何资金变动**的流水不要留在待分类（会永远等人来补规则），也不要硬造分录
（借=贷会落在同一账户，被 `book()` 拦下变成「借=贷同账户，需修映射」的假问题）。
新增了 `entry_type: no_entry`：不生成分录，记录进「配对与问题」表（类型「不生成凭证」），
同时计入 `skipped` 使条数勾稽仍算得平。两处用法：
① 蚂蚁财富内部「转换至」（钱在同一个平台的基金间换持仓）；
② 平台订单「交易关闭」**且账单没写支付方式**（新增 `when.method_empty: true` 条件）＝ 付款没走到扣款。
写了支付方式的「交易关闭」是已扣款后全额退回，**必须正常入账**，否则那几张退款会把费用冲成负数。

## 两个会静默出错的字符串陷阱

- **`summary_not_any: ["退款"]` 太宽**：商家的政策文案里有「不退款」（如「…不支持退款｜服饰装扮」），
  会把真实消费整批挡在所有消费规则之外、落进待分类。判据要写成 `["｜退款", "退款-"]`
  （真退款的摘要是「退款-<商品>｜退款」或「<商户>｜<商户>-退款」）。
- **`keyword_accounts` 里「余额宝」必须排在「支付宝」之前**，否则「余额宝-转出到银行卡」的出资方
  被解析成支付宝余额（1012），1101 与 1012 的增减互换（每月 8,342.37 这类赎回记成「支付宝余额减少」）。

## 新增账户 / 新来源的接线清单（京东那次踩全了，照做）

0. **先问清「这是账户还是入口」**：银行/平台那种「一个来源对应一套账单、每笔只能有一种业务」的
   按账户建档案；「人工补录」这种**一个入口装多种业务**的，文件名/档案只定入口，
   **业务类型由每行自己点名**（`业务类型` 列 + 规则 `business_any`）—— 写 `{sources: [manual]}`
   这种来源级兜底规则，会把将来的其它业务（对方取回/手工更正）一并吞掉
   （同「平台购物规则吞掉还款」那个坑）。没点名/点错名 → 不命中 → 待分类。
1. **先档案、再 skill、后业务**：`Config/bank_profiles.yaml` 加一段 + `skills/<账户>-statement/` 写清文件形态与
   已核验锚点；锚点对平后才开始记账。
2. **档案里必须写 `source:`（bank/alipay/wechat/jd/manual）并建同名解析模块**：`source` 决定用
   `Scripts/parsers/` 里哪个模块解析，也牵连 rules 的 `sources` 白名单、books 的平台侧配对。
   漏了会退回 `parsers.base.SOURCE_BY_PROFILE` 的兜底表，认不出就**静默把该账户当银行**
   （被塞进银行勾稽、被 `sources: [bank]` 的规则命中 —— 最坏的静默错误）。
3. **来源键会牵连三处**：`rules` 的 `sources` 白名单、`books._PLATFORM_SOURCES`（通用「卡结算并进银行」只给
   支付宝/微信 —— 京东的行是按订单/支付方式展开的，套用会把「白条还款」这种京东内部动作误配掉）、
   `books._MONEY_ACCOUNT_FALLBACK`（`$source` 兜底）。
4. **金额列带括注/说明的用档案 `amount_strip`**（京东 `150.98(已全额退款)`、`74.88(已退款1.92)`），取值一律走
   `parsers.amount_of()`（京东模块会检查档案有没有写 `amount_strip`，缺了直接报错）；`split.py` 里也算这个函数，
   否则拆分件统计与账本口径不一致（不清洗会被 `money.D` 判成 0.00 → 静默丢笔）。
5. **交易单号不唯一就用 `ref_join`**（京东：一笔订单拆成「余额+白条」两行、原消费与全额退款行共号）。
   **写档案列键**（`[date, ref, method]`），不是表头中文名 —— 写中文名会取不到值而静默退回兜底单号
   （只含日期+金额），同额同日的两笔随后会被「重复流水」护栏丢掉一笔。
6. **`split.py` 的说明块正则是一家的形状**：新平台的「共N笔记录 / 收入：N笔，X元 / 支出：N笔(含…)，X元 /
   日期区间：…至…」都要扩进 `_COUNT_RE`、`_BUCKET_RE`、`_DECLARED_RANGE_PATTERNS`、`_DESC_HINT`，
   否则拆分件统计读不出、空月不出文件、拆分说明插错位置；区间行（`日期区间`）也要改写成当月，
   不然抬头声明覆盖 8 个月而内容只有一个月。改完按 Step 0 的四步复核（行数关系／逐文件解析对账／多重集全等）。
7. **新科目同步 `stats.py`，并逐期确认两道勾稽为 0、费用率 + 储蓄率 = 100%**（新来源只做条数勾稽——
   平台账单没有余额列，金额勾稽只对银行账户做）。

## 多主体（两人 / 共同财产）并入同一账套

把第二个人的账户并进来做合并分析时，**代码零改动**，只改数据：

1. `Config/bank_profiles.yaml` 同一档案下加**账号段**（她的 3572 / 0504 / 支付宝 8239 / 微信昵称）：
   各自 `account_label` 带人名、`money_account` 指向新账户键。
   ⚠️ **没加账号段就会静默套用本人账号**（文件名没账号段时回退档案默认）—— `split` 会把她的流水
   命名成本人的按月文件，同名已存在则跳过（看着像没事），加 `--force` 就直接覆盖，不可逆。
   先 `split --dry-run` 看「导出账号」判成谁，再写盘。
2. `Config/account_map.yaml`：`accounts` 加她的资金账户（明细带人名）；`settlement_accounts`
   加她账单里出现的**每一张**卡，含只作为「钱的出处」出现、没有流水导出的卡（否则 `$settlement`
   直接报错停下）。
3. **两人互转 = 内部划转**：把她的卡号登记进 `own_accounts` 即可（**不必**改 `own_names`）——
   `own_account_hit()` 命中已登记卡号就算「自有账户」，`own-account-move` 记成资金 ↔ 资金，
   两端都导出时 `pair_own_account_transfers` 只保留转出侧。仍然**只认卡号**：她账单里若干笔
   「对方=她自己姓名」其实是提现/余额宝转出到自己的卡，按卡号登记恰好把这两类分开。
4. 合并统计天然成立（同一账套）：各期账本与 `trend` 就是两人合计；要分人看就按账户明细。

## 两个会静默出错的陷阱

0. **手写 CSV 的一个半角逗号会把后面所有列冲歪**（人工补录、拆分件）：不会报错，只会把
   「收入/2000.00」读成「收支=000、金额=收入」—— 那笔静默变成 0.00 元中性流水。两道防线：
   ①该来源的档案开 `strict_columns: true`（列数≠表头就报错）②用 `csv.writer` 写文件
   （含逗号的字段自动加引号），手写就自己加引号或用全角逗号。新写任何手编 CSV 后先跑 `normalize`
   逐笔核对**笔数/方向/金额**三项 —— 只看「解析条数对得上」发现不了这种错。

1. **本工具自己的产物不能被当成流水再解析**：中间表放在 `Running Account/流水中间表/`，
   而 `parsers.normalize_dir` 是 `rglob("*")` 递归扫描 → 必须靠 `paths.RUNNING_TABLE_PREFIX`
   前缀过滤（已实现）；否则会看到 `⚠ 解析失败 流水中间表_YYYY-MM.csv`，或更糟——把中间表
   当新流水重复入账。同理排除 Excel 锁文件 `~$*`。
   改名后的副本同理：内容相同的文件只解析一份（见上面「解析器按来源分模块」一节）。
2. **平台账户的余额不可勾稽**：账单无余额列，「收/支」是用户收付口径（含卡代付），小荷包是
   有独立进出的子池。不要用"结算方式过滤"去推算平台余额——推出来的数字与记账口径会差几千，
   那种数字不可信；平台侧只做条数勾稽，金额勾稽只对银行账户做（银行流水自带余额列）。

  「京东业务：白条主动还款」），不能只写「白条还款」。
- **还款额含未拆分的利息**：2026-01-05 还 35,087.50、2026-05-07 还 35,014.50 都对 35,000 本金多出几十元。

  负债（表上会出现小额借方余额），把差额金额写进需确认事项等人工核定，不猜。
- **交付前的勾稽有两套，别只看一套**：统计表里的「①资产−负债−权益」与「②现金净增加额−货币资金净变动」
  只证明表内自洽；**逐账户银行勾稽在「配对与问题」表**（`book`/`month` 会把不平静的打到控制台）。
  只看统计表那两条就宣称“勾稽全为 0”是不够的 —— 01–04 曾各有 1,000.00 / 4,000.64 / 8,342.37 / 2,697.00
  的银行差额停留在那里，就是因为只看了统计表。**逐期跑完必须把 配对与问题 里的银行行扫一遍（须为「一致」）。**
- **提现与银行入账的配对有三个坑**（都在 `books.pair_internal_transfers`，都是“两侧各记一次”）：
  ①平台侧配对池不能限定 `收支 == "out"`：「零钱提现」「余额宝-转出到银行卡」在账单里是「不计收支/收入」，
  限定 out 就进不了池子 → 银行侧照样入账；②银行侧识别词要含「转出到卡」（「银联入账｜余额宝转出到卡」
  既无「提现」也无「支付宝」字样）；③**提现要扣手续费**，两侧金额不等（4,000.26 ↔ 到账 3,996.32，
  1,000.00 ↔ 999.00）→ 严格同额配对永远配不上，要按「平台额 − 到账额 ∈ (0, 0.1%]」容差配，
  并把差额当手续费：平台侧按「到账净额 + 5603 财务费用—手续费」入账。
  另外 `platform-withdraw-to-bank` 的 `to` 不能写死某张卡（要 `$settlement` 看「收/付款方式」），
  否则「淘宝签到提现」这类没写收款卡的行会凭空借记银行 —— 流水里根本没这笔，勾稽当场报差。
- **个人之间的转账默认按 收入 / 费用 处理**（用户口径）：转给个人 → 借 `5602 管理费用—生活支出-个人转账`；
  个人转来 → 贷 `5301 营业外收入—个人转入（非借款）`。**不要默认挂 `1221 其他应收款—个人往来`**：
  默认性质不是借款，挂应收款等于把每笔转账都当成待收回的债权。1221 只留「个人往来」「待确认款项」
  「代垫差旅费报销」这类性质明确/待定的划转；**本人自有账户互转不挂 1221**（见下一节：按卡号认账户）。
- **退款必须走 `refund`（贷 原费用，冲减），不能当新支出/新收入**：平台把退款记为「不计收支」或摘要带
  「退款-<商户>」，若照旧让消费类规则按商户名命中，就会「退款记成花钱」，一笔钱虚增两次。
  三条护栏缺一不可：①消费类规则统统加 `summary_not_any: ["退款"]`（宁可落待分类，也不要静默记错）；
  ②给可判商户写 `refund-*` 规则（priority 要高于同名消费规则，如 86 > 80），`params.money: "$settlement"`
  让退款回到原出资渠道（花呗→贷方冲减花呗、小荷包→回小荷包）；③**平台侧与银行侧退款要配对去重**：
  「转账-退款」（结算方式写着某张卡）与银行「网上快捷退款」是同一笔，保留银行侧（`books.pair_card_funded`
  里按 `退款 + 卡结算 + 同额银行入账` 判，别只加进 `_PLATFORM_WITHDRAW` 关键词表，会误伤提现配对）。
  同理 `bank-in-from-platform` 必须加 `summary_not_any: ["退款"]`——银行的「网上快捷退款」曾被它当成
  「从微信/支付宝提现到卡」，同一笔退款在两侧各记一次入账。
- **`settlement_accounts` 按「最具体关键词优先」匹配，且没有任何通用兜底**（`books._settlement_account`
  取最长关键词，同长才按表序）：每张卡/信用工具**单列一条**，绝对不写 `{when: ["信用卡"]}` 这种泛词
  把出资方指向某一张卡 —— 原先通用「信用卡」默认判成 9393，任何没单列的信用卡（如 5235）的消费
  都会被静默记到 9393 头上。取最长关键词还順带修好了「折扣字样抢走出资渠道」：
  「中国银行储蓄卡(3358)&花呗金」里的「花呗金」只是抵扣，钱从 3358 走。
  没命中且结算方式里带卡/信用工具（储蓄卡/信用卡/花呗/白条/分分卡/先享后付/借呗）→ **报错停下**

  已知地雷：京东「先享后付」目前只有 3 笔 0.00（不入账），一出现真实金额就会报错 —— 需先定它挂哪张负债。
- **新增负债/资产科目后，`stats.py` 要同步三处**（否则表长得像对的、其实自相矛盾）：
  ①`BLOCK_OF` 归类（靠 CASH/ASSET/LIABILITY/INCOME/EXPENSE_CODES 集合）；②**报表块的逐科目列示**

- **收入/费用合计必须用净额（借方 − 贷方 ／ 贷方 − 借方）**：一旦出现退款冲减（贷 费用），
  只按毛发生额算合计会把冲销漏掉，净利润不对，且「资产 − 负债 − 权益」与桥接勾稽同时留残差
  （2026-08 残差 1,013.81 全是退款冲减额）。**勾稽不为 0 就是账没算全，先查这种口径漏项。**
- **银行「速汇/快捷」类流水的对方户名常是银行自己**（如「宁波银行股份有限公司」+对方开户行「美团支付(钱袋宝)」

## 交付的 xlsx 必须能被 Excel 双击打开（血泪教训）

症状：**Excel 双击时报「发现…中的部分内容有问题，是否让我们尽量尝试恢复？」**，
但 LibreOffice / pandas 都能正常打开 → 光用 LibreOffice 验证**发现不了**这类问题。

两个真实原因（都踩过）：
1. **冻结窗格与 selection 不一致（本次的真凶）**：`ws.freeze_panes = "A2"` 会写出
   `<pane ySplit="1" topLeftCell="A2" activePane="bottomLeft" state="frozen"/>
    <selection pane="bottomLeft" activeCell="A1" sqref="A1"/>`
   —— activeCell A1 落在**冻结区内**却声称自己在 bottomLeft（下半区），自相矛盾。
   Excel 自己写的文件是 `activeCell` 位于下半区（如 `H94`，行号 > ySplit）。
   **修法：统一用 `export._freeze(ws)`**（设完 freeze_panes 再把 selection 重置为 A2）。
2. **写空字符串 `""`**：openpyxl 会产出 `<c r="M437" t="inlineStr" />` 这种自闭合单元格，
   而 `t="inlineStr"` 必须带 `<is>` 子元素 → 畸形 part。**任何空白文本一律写 `None`**
   （`export._t()` 就是干这个的），写 None 则根本不生成该单元格。
3. **每处写文本都必须过 `_t()`**：`规则命中` 表曾直接 `ws.append([hit["凭证号"], …])`，
   而未命中规则的流水 `凭证号` 是空串 → 写出畸形 inlineStr → `check_parts()` 直接拒绝交付，
   整个月一本账都出不来（2026-07 踩，报 `sheet5.xml：6 个畸形单元格`）。
   这种 bug 会潜伏很久：只要某期**零待分类**（从未命中空串）就一直不发作（2026-08 恰好如此）。
   `export._sweep_blank_text()` 是兑底网（把漏网的空串退化成空单元格并警告），**真正的修法是那一处用 `_t()`**。

已被 **A/B 实测否定**的怀疑（别再往这个方向修）：openpyxl 把字符串写成内联、不生成
`xl/sharedStrings.xml`、字体定义残缺、`docProps/app.xml` 的 `AppVersion` 非 Excel 格式 ——
用真实数据造的「裸数据」「仅筛选」两个 openpyxl 产物，Excel **都能正常双击打开**。
所以 openpyxl 本身可用，病灶只在具体写法。

**比对两次运行的产物不要用字节哈希**：`export_workbook` 每次都由 openpyxl 写
`docProps/core.xml` 的 `dcterms:created/modified`，因此 xlsx 的 sha256 每次都不一样（其余 12 个 part
（含 5 张工作表）逐字节相同）。稳定口径只有两种：① 逐工作表读回比较单元格值
（`verify_workbook()` 的输出，或遍历 `ws.iter_rows(values_only=True)`）；② 解包后比每个 part 的 CRC
（相同 = 内容相同，差异只在时间戳）。**别再拿 `记账凭证表_校验.json` 比对 —— 该文件已按用户要求删除。**

**排查方法（比读 XML 猜快得多）**：拿真实数据造一组最小对照文件，一次只加一个特性
（裸数据 / +自动筛选 / +冻结 / +样式 / +全都有），让用户各双击一次 —— 哪一步开始报错，
元凶就在那一个特性上。本次就是靠这招从 5 个特性里锁定"冻结窗格"。

**对策（已写进代码，别再手工修）**：
- `export._freeze(ws)`：冻结首行并把 selection 修正到冻结区外（见上）。
- `export._t(value)`：空白文本一律写 `None`，杜绝空的 inlineStr 单元格。
- `export.check_parts()`：交付前硬门禁，六项检查 —— ① zip 完好 ② 每个 part 合法 XML
  ③ 无畸形内联单元格 ④ 每个 part 都在 `[Content_Types].xml` 声明 ⑤ 工作表引用的 `r:id`
  在 `_rels` 里真实存在 ⑥ **冻结窗格与 selection 一致**。不通过就抛 RuntimeError，
  **宁可失败也不交坏文件**。
- `export.excel_normalize()`：LibreOffice 洗包，**默认关闭**（`normalize=False`）。
  它曾被我当成对策但没解决问题；现在只作为兜底手段保留，且洗包前后必须各跑一次
  `verify_workbook()`，两者不同就拒绝交付。
- 附带：`parsers.normalize_dir` 必须跳过中间表自身产物与 Excel 锁文件 `~$*`。

## 禁止事项

- 不猜科目、不猜税率、不编造交易对手：无法判断 → 待分类；
- 不猜账户：自有人账户划转的对方账号没登记 → **报错停下**（`AccountUnregistered`），不许用「本人其他账户」
  这类笼统明细兜底；出资卡的「结算方式」没登记 → 同样报错，**不许默认成某一张卡**（也不许回退成平台余额）；
- 不修改原始导出文件（只读处理，中间表另存）；
- 税额拆分只在有明确税率配置时执行，`tax_confirmed: false` 时税额行必须带「税率待确认」备注。
