# Repo-root skill tooling

Two scripts live at the repo root rather than inside a skill: they act on the whole `skills/` tree, and a
file inside a skill directory is scanned, shipped and listed in that skill's generated tree.

## `auto-generate-skill-structure.py` — the generated `## Skill Structure` section

A per-skill inventory tree bracketed by two `<!-- Generated by Scripts -->` markers, so a skill's own file
list cannot drift from disk. The `## Skill Structure` heading itself is hand-written *outside* the markers;
only the block between them is owned by the generator.

Rendered shape (one fenced block):

```
<skill-dir-name>/
├── SKILL.md  (74 lines)
├── references/
│   ├── a.md  (189 lines)
│   └── b.md  (327 lines)
└── scripts/
    └── gen.py  (142 lines)
```

### One generator per repo, not one copy per skill

A repo that holds a family of skills (`skills/<name>/SKILL.md` × N) keeps the generator **once**, here, and
it walks the skills root. N identical per-skill copies drift, and every content edit has to be applied N
times; collapsing them is a valid request on its own — delete each `skills/*/scripts/<gen>.py` and its
now-empty `scripts/` dir, then regenerate, because those trees still list the file you just deleted (and
each `SKILL.md`'s own line count shifts by the lines removed).

```bash
python3 scripts/auto-generate-skill-structure.py                        # every skill
python3 scripts/auto-generate-skill-structure.py --check                 # exit 1 if any is stale
python3 scripts/auto-generate-skill-structure.py install-hermes-skills   # only these
```

### Status semantics

One line per skill, `<path relative to the repo root>: <status>`, then a `N skills: …` summary. Exit code
is 1 only under `--check`.

| State | Printed | Fails `--check` | Why |
|---|---|---|---|
| section rewritten | `rewritten` / `stale` | yes | drift |
| section already current | `already up to date` | no | second run is the no-op proof |
| 0-byte or whitespace-only `SKILL.md` | `skipped (empty placeholder)` | no | WIP skeleton; writing into it would produce a skill with no frontmatter |
| non-empty `SKILL.md`, no markers | `skipped (no <!-- Generated by Scripts --> markers to fill)` | yes | a real skill missing its inventory — actionable |
| skill dir with no `SKILL.md` | `skipped (no SKILL.md)` (the path shown is the directory) | no | work in progress |

Classify skip reasons, do not lump them into one counter: a gate that fails on WIP placeholders gets turned
off, and one that passes on a skill missing its section never catches anything. **`remove-hermes-skills` is
the pack's one 0-byte `SKILL.md`** — reported as `skipped (empty placeholder)`, and deliberately *not* a
`--check` failure, so a repo-wide `--check` exits 0 on it. It joins the generated set the moment it carries
content and a marker pair (0 bytes install and `inspect` returns `None` for it in the meantime — see
`skills/install-hermes-skills/references/install-hermes-skills-diagnosis.md`).

### Render contract

- Files before directories at every level; `SKILL.md`, then `README.md`, then other files alphabetically;
  directories alphabetically. Directories containing only skipped junk are not rendered.
- `(N lines)` for `.md .py .sh .txt .json .yaml .yml` only; other files render bare.
- Skip `.DS_Store`, `__pycache__`, `.git`, `.idea`, `.vscode`, `*.pyc`, `*.pyo`.
- The block lists `SKILL.md`'s own line count, so one pass is not a fixed point: the script iterates the
  in-memory candidate (feeding the candidate's own length through an override) until the block stops
  changing, then writes once — otherwise `--check` reports stale forever.
- Print paths relative to the repo root, so a run is readable and diffable from anywhere.

### Verification recipe

1. Run the generator, then `--check` scoped to what you touched; expect `0 stale` and exit 0. **Scope both
   the run and the check** (`… install-hermes-skills`): a repo-wide `--check` also reports other writers'
   skills, exits non-zero on their drift, and invites you to regenerate work that is not yours. Name any
   other stale skill in the report and touch nothing.
2. Cross-check the rendered counts against disk, never by eye — a wrong count is invisible to a reader:
   `python3 scripts/verify-skill-package.py skills/<name>` does exactly this comparison.
3. Drive the branches from a throwaway skills root instead of mutating the repo: build
   `<scratch>/skills-root/{alpha,beta,gamma,delta}/` (markers+stale / non-empty without markers / 0-byte /
   no `SKILL.md`), run with `--skills-root <scratch>/skills-root`, and assert the exit codes of `--check`
   before, the write run, and `--check` after.
4. Grep the repo for references to any generator path you deleted, and remove the `scripts/__pycache__`
   that `python3 -m py_compile` leaves behind, so it is never staged.

### Consequences to report, not to paper over

- Skills already installed into a profile keep their own `scripts/` copy and their own tree until the hub
  reinstalls or updates them; a repo-side move does not propagate by itself. Say so and name the installed
  paths — do not hand-edit the installed package.
- A family repo usually holds 0-byte placeholder skills alongside finished ones. They are reported as
  `empty placeholder` by design, and join the generated set automatically once they carry content and the
  marker pair.

## `verify-skill-package.py` — tree counts and pointers, one command

```bash
python3 scripts/verify-skill-package.py skills/<name>
python3 scripts/verify-skill-package.py skills/<name> --allow-pointer references/a.md
```

Stdlib only, no dependencies, exit 1 on any problem and 2 when the directory has no `SKILL.md`. Two checks:

- **tree vs disk** — inside the marker block, every `(N lines)` entry must match the file's real line
  count and the tree heading must equal the directory name. The block is generated, so a mismatch is a
  generator bug: re-run the generator, never hand-edit the block. A 0-byte / whitespace-only `SKILL.md`
  is a WIP skeleton and reports clean — the generator's own classification, which is what keeps a
  repo-wide run green on `remove-hermes-skills`, the pack's one placeholder.
- **pointers** — every `references/<name>.md` named outside a fenced block must exist in this package **or
  in a sibling skill** under the skills root (`--skills-root`, default the parent of the skill dir), because
  that is how one skill in this pack points at another. Text inside ``` fences is ignored: a verbatim
  receipt may legitimately name a file that is not ours.

`--allow-pointer references/x.md` (repeatable) declares a name that is evidence rather than a pointer — a
measured fixture, an illustration. Declarations are **printed** as a count, never silently skipped, so a
real pointer can never hide behind one.

**Declared exemptions in this pack:** `references/a.md` and `references/00-overview.md`, both in
`install-hermes-skills/references/install-hermes-skills-registry-routes.md`, are fixture names inside a
verbatim extractor transcript (what the fetcher requested, and what `skill_view` listed). They are citations
of measured behaviour, so renaming them to a shape would falsify the receipt. Run:
`python3 scripts/verify-skill-package.py skills/install-hermes-skills --allow-pointer references/a.md
--allow-pointer references/00-overview.md` → exit 0.

The two scripts also run against a pre-change worktree when a rename is in flight, so the before/after
pointer lists can be diffed instead of compared against zero
(`skills/install-hermes-skills/references/install-hermes-skills-renaming-a-skill-pack.md` §5).

## Workflow

Run the generator after the last content edit of a session — after adding, renaming or deleting any
reference or script — then `verify-skill-package.py` on the skills you touched, then commit. Both belong in
the same commit as the edit they describe.
